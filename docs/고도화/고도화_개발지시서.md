## 0-2. 왜 이렇게 설계했나 (설계 이유 전체)

> 구현 전에 이 절을 먼저 읽는다. 여기 적힌 이유를 바꾸면 이 파일 전체를 다시 검토해야 한다.
> 그림: 목표 구조는 `고도화_구조도.png`, 섹션 2-1의 ASCII 그림.

### 0-2-1. 왜 구조를 바꾸나

| 문제 | 현재 코드에서 실제로 일어나는 일 | 목표 구조의 해결 |
|---|---|---|
| 클릭마다 같은 행을 갱신 | `campaign_stats` 한 행을 모든 클릭이 잠금 → 같은 캠페인 클릭이 몰리면 대기 | 클릭은 Kafka로만 보냄 (DB 쓰기 0) |
| 집계를 원본 스캔으로 계산 | 추이·연령대별 조회가 `click_events`, `ad_impressions`를 매번 셈 | 분·시간·일 집계 표를 ClickHouse MV가 미리 계산 |
| 원본이 DB에만 있음 | 재계산을 하려면 DB를 다시 읽어야 함, 큰 표를 오래 두면 DB가 무거움 | 원본은 S3 파일 (싸고 오래 보관), DB에서는 뺌 |
| 재시도로 인한 이중 차감 | 배너 요청이 재시도되면 차감과 노출이 두 번 생김 | 요청 ID 유니크 표로 차감을 한 번으로 제한 |

- 목적은 **DB 부하를 줄이는 것**과 **Kafka·ClickHouse 구조를 직접 만들어 보는 것**(학습)이다. 운영 규모 목표는 측정 뒤에 정한다.
- 모놀리식 1개 서비스 안에서 한다. 서비스 분리는 하지 않는다. 운영 부품을 최소로 하려고 Kafka 브로커는 1대, Redis는 추가하지 않는다.

### 0-2-2. 왜 노출과 클릭을 다르게 처리하나

| 구분 | 노출 | 클릭 |
|---|---|---|
| 돈이 움직이나 | **예 (예산 차감)** | 아니오 (집계용) |
| 정확해야 하는 곳 | 예산 원본 (PostgreSQL) | 광고주 숫자 (확정은 재계산) |
| DB에 쓰나 | 예 (차감, 기록, outbox를 한 트랜잭션) | 아니오 |
| Kafka로 보내나 | 예 (outbox 릴레이 경유) | 예 (바로 발행) |

- 노출은 예산과 엮여 있어서 DB 트랜잭션 안에서 확정한다. 클릭은 돈과 무관하므로 DB를 빼도 된다.
- 노출이 클릭보다 훨씬 많다. 그래도 노출을 DB에 두는 것은 예산 정확성 때문이다. 노출을 Kafka로 보내는 것은 집계 숫자를 ClickHouse에서 보기 위해서다.

### 0-2-3. 왜 트랜잭션을 이렇게 묶었나

- **차감 + 노출 기록 + outbox 행을 한 트랜잭션**으로 묶는다.
  - 차감과 기록이 따로 놀면 예산이 맞지 않는다 → 같이 성공하거나 같이 취소.
  - Kafka 발행은 DB 트랜잭션에 넣을 수 없다 (두 시스템은 한 트랜잭션으로 못 묶인다). 그래서 **DB에 발행 대기 행을 같이 쓰고**, 릴레이가 나중에 Kafka로 보낸다. 이것이 아웃박스 패턴이다.
- 예산 초과는 **조건부 UPDATE** (`spent_total + 입찰가 <= total_budget`)로 막는다. 아웃박스가 막는 것이 아니다.
- 클릭은 요청 경로에서 DB에 쓰지 않는다. Kafka 발행이 성공하면 201, 실패하면 DB 실패 표(`click_fallback`)에 저장하고 202, 둘 다 실패하면 503. 음악 앱은 실패분을 로컬 저장소에 두고 다시 보낸다 (A-15).

### 0-2-4. 왜 이렇게 중복을 처리하나

중복은 **어디서 생기는지**에 따라 처리 위치를 나눴다.

| 중복 원인 | 해결 위치 | 이유 |
|---|---|---|
| 배너 요청 재시도 (차감 이중) | 요청 ID 유니크 표 (DB 트랜잭션 안) | **돈과 직결**되므로 실시간에서 막아야 한다. DB 한 트랜잭션이 가장 확실하다 |
| 릴레이 재발행 (outbox 완료 표시 전에 죽음) | 재계산 (`notification_id` GROUP BY) | 돈과 무관한 집계 복사본이다. 실시간에서 막으려면 비용이 크다 |
| 클릭 중복 (사용자가 여러 번 누름, 발행 재시도) | 재계산 (`notification_id` GROUP BY) | 클릭은 집계용이고, 요청마다 막으면 DB 읽기·쓰기가 늘어난다 |
| 컨슈머 재처리 (저장 후 커밋 전 죽음) | 재계산 | 파일에 같은 줄이 두 번 들어가도 재계산이 한 번으로 센다 |

- 노션의 원칙: 두 번 해도 되는 처리(상태 설정)는 그대로 두고, 두 번 하면 안 되는 처리(잔액 증가)는 처리 기록으로 막는다. 차감이 바로 후자다.
- **실시간 클릭 중복을 ClickHouse에서 막지 않은 이유**
  - `ReplacingMergeTree`는 병합 시점을 보장할 수 없어서 실시간 값이 항상 맞지 않는다.
  - 원본 표를 ClickHouse에 두고 `GROUP BY`로 세면 조회가 느려지고 저장 비용이 늘어난다.
  - 클릭 숫자는 하루 뒤 확정이면 광고주 화면에 충분하다. 결정 근거는 `고도화_계획.md` 2026-11-21 결정 절.
- 책(6장)은 실시간에서도 정확히 한 번을 목표로 분산 트랜잭션을 권한다. 우리는 구현 비용이 크고 학습 목적에 맞지 않아 쓰지 않는다.

### 0-2-5. 왜 이 정도 손실을 감수하나

아래 항목은 **의도적으로 감수**하는 것이다. 각 항목에 대책이 있다.

| 감수하는 것 | 얼마나 | 왜 괜찮은가 | 대책 / 확인 방법 |
|---|---|---|---|
| 실시간 클릭·노출 숫자가 잠깐 부풀어 보임 | 중복 비율만큼 (보통 작음) | 확정은 다음 날 03:00 재계산 | 대시보드에 "잠정" 표시 |
| Kafka가 죽었을 때 클릭 | 장애 시간 동안 | 202로 `click_fallback`(DB)에 보관 후 Kafka 복구 뒤 재전송 | 202 수, `click_fallback` PENDING 수 모니터링 |
| DB 실패 표도 쓸 수 없는 순간 (DB와 서버가 동시에 죽음)에 앱에서 누른 클릭 | 아주 드묾 | 음악 앱 로컬 재시도(A-15)가 보완. 클릭은 과금과 무관 | 503 수 확인 |
| Kafka 브로커 1대 장애 시 최근 데이터 손실 | 브로커 디스크가 죽으면 7일 안의 메시지 | 학습용 1대 구성. 운영 승격 때 3대로 | 운영 전 재검토 항목 |
| 재계산 48시간 밖의 늦은 중복 | 극히 드묾 | 조정(03:30)이 차이로 드러낸다 | 조정 경고 확인 |
| 요청 ID 7일 보관 후 삭제 | 7일 넘은 재시도 | 재시도는 보통 몇 분 안에 일어남 | 보관 기간 재검토 |
| ClickHouse 장애 시 대시보드 숫자 지연 | 장애 시간 동안 | Kafka가 7일 보관하고, 복구 후 MV가 따라잡음 | 복구 뒤 행 수 비교 |
| 릴레이 재발행으로 Kafka 사본 중복 | 드묾 | 재계산이 정리 (돈은 DB 원본) | 재계산 중복 제거 수 기록 |

- **감수하지 않는 것** (반드시 막는다):
  - 예산 초과 차감 → 조건부 UPDATE
  - 같은 요청 ID로 인한 이중 차감 → 요청 ID 유니크 표
  - 노출은 됐는데 outbox 행이 없는 것 → 같은 트랜잭션
  - S3에 저장되지 않은 채 Kafka 커밋 → 저장 후 커밋 순서 고정

## 1. 현재 구조 (코드 기준 사실, 2026-11-22 develop `9024bdb` 기준)

### 1-1. 그림

```
[배너 요청] GET /api/v1/banners/match?targetUserId=
   └ BannerService.matchBanner
       ├ 후보 조회 (연령대·성별·기간 일치, 진행 중)
       ├ BidAuction.pick (입찰가 비례 선택) → BidAuction.charge (2등 + 1원)
       ├ campaigns 조건부 UPDATE (deductBudget) → 성공하면
       └ 노출 저장 (ad_impressions) + campaign_stats.sent_count +1  ← 같은 트랜잭션

[클릭] POST /api/v1/clicks {notificationId}
   └ ClickService.recordClick (한 트랜잭션)
       ├ ClickEventRepository.insertIfAbsent → click_events INSERT ON CONFLICT DO NOTHING
       └ campaign_stats.click_count +1 (새 클릭일 때만)
       → 201(새 클릭) / 200(중복)

[대시보드]
   ├ 추이: GET /campaigns/{id}/stats/timeseries → ad_impressions, click_events 원본을 date_trunc로 셈
   ├ 누적 숫자·SSE: campaign_stats (2초 폴링)
   └ 연령대별: GET /campaigns/{id}/stats/by-age → 원본 표 조인
```

- Kafka, ClickHouse, Redis, 아웃박스: **없음** (`docker-compose.yml`에는 P3에서 추가라고만 적혀 있음).
- S3: 배너 이미지 업로드용 SDK만 있음. 이벤트 원본 저장 없음.
- 현재 클릭 누적과 노출 누적은 `campaign_stats`의 숫자이다.

## 2. 목표 구조

### 2-1. 그림

```
[배너 요청] GET /api/v1/banners/match  (헤더 X-Request-Id 필수)
   └ 한 트랜잭션 (PostgreSQL)
       ① banner_requests 에 request_id 삽입
            이미 있으면 → 차감·기록 없이 저장된 결과 반환 (끝)
       ② campaigns 조건부 UPDATE (차감)  … 실패하면 다음 후보
       ③ ad_impressions 기록
       ④ campaign_stats.sent_count +1
       ⑤ outbox 행 추가 (status = PENDING)
       ⑥ banner_requests.notification_id 기록
   └ 커밋 후 응답

[릴레이] 1초마다 (스케줄러, 담당 A)
   └ outbox 에서 PENDING 행을 outbox_id 순으로 읽음 → Kafka ad-impressed 발행 → PUBLISHED

[클릭] POST /api/v1/clicks {notificationId}   (요청 경로 DB 쓰기 없음)
   └ ad_impressions 를 PK로 1회 읽어 age_group·gender·target_user_id 확인 (없으면 404)
   ├ Kafka ad-clicked 발행 성공 → 201 (중복이어도 201)
   ├ 발행 실패 → DB click_fallback 저장 → 202 (재전송 예정)
   └ 둘 다 실패 → 503

[실패 재전송] 10초마다 (담당 A): click_fallback 의 PENDING 을 Kafka ad-clicked 로 발행 → SENT
[클릭 DB 사본] (담당 C, C-8): Kafka ad-clicked 를 배치(500건 또는 1초)로 읽어 PostgreSQL click_events 에 ON CONFLICT DO NOTHING
[음악 앱 재시도] (담당 A, A-15): 실패한 클릭을 로컬 저장소에 두고 다시 보냄. 201·202·404 면 제거

[Kafka]
   ad-impressed, ad-clicked : 파티션 3, 키 campaign_id, 보관 7일, 브로커 1대

[ClickHouse] (담당 B)
   impressions_kafka ─MV→ impression_facts (분) ─MV→ impression_facts_hour ─MV→ (일은 분에서 MV)
   clicks_kafka      ─MV→ click_facts      (분) ─MV→ click_facts_hour      ─MV→ (일은 분에서 MV)

[재집계 저장] (담당 C)
   ad-clicked, ad-impressed ─ 컨슈머(raw-archive) ─→ S3 raw-clicks/, raw-impressions/  (저장 성공 후 커밋)

[재계산] 매일 03:00 (담당 C)  ─ S3 원본 (최근 2일) → ClickHouse *_stage → REPLACE PARTITION (분·시간·일)

[조정] 매일 03:30 (담당 C) ─ 개수 4쌍 비교 → recompute_log 기록, 차이는 경고

[조회] (담당 B)
   추이 (timeseries)·상위 N·연령대별 → ClickHouse 집계 표
   누적 노출·예산 → PostgreSQL (campaign_stats, campaigns)
   누적 클릭 (목록·상세·SSE) → ClickHouse 합계로 전환 (섹션 7-4)
```

### 2-2. 목표 구조에서 바뀌는 것 (요약)

| 항목 | 현재 | 목표 |
|---|---|---|
| 클릭 저장 | click_events + campaign_stats (DB, 요청 경로) | 요청 경로는 Kafka ad-clicked만. DB 사본 click_events는 사본 컨슈머가 배치로. 실패분은 click_fallback |
| 클릭 응답 | 201 / 200 | 201 (전송됨, 중복 포함) · 202 (실패 표 보관) · 503 (둘 다 실패) · 404 (노출 없음) |
| 클릭 중복 제거 | ON CONFLICT (DB) | 없음 (실시간) → 재계산에서 정리 |
| 노출 발행 | 없음 | outbox → 릴레이 → Kafka ad-impressed |
| 배너 중복 차감 | 없음 (재시도하면 이중 차감) | banner_requests 유니크 표로 차단 |
| 집계 | 원본 스캔 | ClickHouse MV (분·시간·일) |
| 원본 | DB 표 | S3 파일 |
| 확정 | 없음 | 매일 03:00 재계산 |
| 검증 | 없음 | 매일 03:30 조정 |
| Redis | 없음 | 없음 (추가하지 않음) |

## 3. 공통 계약 (세 담당 모두 이 섹션을 따른다)

> 이름·형식을 바꾸려면 세 담당에게 먼저 알리고 이 파일을 고친 뒤 작업한다. 한쪽만 바꾸면 깨진다.

### 3-1. 카프카 토픽

| 토픽 | 파티션 | 키 | 보관 | 생산자 | 소비자 |
|---|---|---|---|---|---|

### 3-2. 메시지 형식 (두 토픽 공통, JSON 한 줄)

```json
{"notification_id":"3f2b8c1e-9a4d-4e7b-8c21-5d6f7a8b9c0d","campaign_id":12,"age_group":"20s","gender":"female","event_at":"2026-11-22 07:30:12"}
```

| 필드 | 타입 | 규칙 |
|---|---|---|
| `notification_id` | String (36자) | 노출 1건의 UUID. 클릭은 노출의 값을 그대로 씀 |
| `campaign_id` | Int64 | 캠페인 ID |
| `age_group` | String | `10s`~`50s`, 모르면 `unknown` |
| `gender` | String | `male`, `female`, 모르면 `unknown` |
| `event_at` | String | 서버가 요청을 받은 시각, **한국 시간, 초 단위**, 형식 `yyyy-MM-dd HH:mm:ss` |

- 노출 메시지: 노출 기록 시점의 `age_group`, `gender`, `shown_at`을 쓴다. `event_at` = `shown_at`.
- 클릭 메시지: `ad_impressions`에서 읽은 `age_group`, `gender`, `target_user_id`, 클릭 요청 시각을 `event_at`으로 쓴다. `target_user_id`는 클릭 메시지에만 있다 (DB 사본 `click_events`용).
- 필드 이름은 snake_case 고정. Java 쪽에서는 `@JsonProperty` 또는 Jackson 전역 snake_case 설정을 쓰지 않고, 레코드에 `@JsonProperty("notification_id")` 식으로 명시한다.

### 3-6. ErrorCode 추가 규칙

- 새 `ErrorCode`는 **담당 A 한 PR에서만** 추가한다 (결정 20).

| 이름 | HTTP | 메시지 | 발생 위치 |
|---|---|---|---|
| `BANNER_REQUEST_ID_REQUIRED` | 400 | `X-Request-Id 헤더가 필요합니다` | 배너 요청 헤더 누락 |
| `CLICK_PUBLISH_FAILED` | 503 | `클릭을 기록하지 못했습니다. 다시 시도해 주세요` | Kafka 발행 실패 |

- 클릭 API의 404 (노출 없음)는 기존 코드 `ErrorCode.IMPRESSION_NOT_FOUND`를 그대로 쓴다.
- 현재 `BannerService.matchBanner(Long targetUserId)`는 `Optional<BannerResponse>`를 반환한다 (후보 없음 = empty). `BannerController.matchBanner`가 `empty`일 때 `ResponseEntity.noContent()`(204)를 돌려준다. 변경 후 시그니처는 `Optional<BannerResponse> matchBanner(Long targetUserId, String requestId)`이고, 컨트롤러 응답 규칙(200/204)은 그대로 둔다.
- 현재 노출 생성 코드는 `AdImpression.builder()...build()`를 쓰고, `notificationId`는 `UUID.randomUUID().toString()`이다 (`BannerService.recordImpression`). 같은 방식을 유지한다.

### 3-8. 트랜잭션 규칙 (공통)

| 작업 | 트랜잭션 | 규칙 |
|---|---|---|
| 배너 요청 (A) | **하나의 DB 트랜잭션** | 요청 ID 삽입 → 차감 → 노출·누적·outbox → 요청 행 갱신. 실패하면 전부 취소 |

### 4-2. 구현 상세

**(a) 배너 요청 — `BannerService.matchBanner(Long targetUserId, String requestId)` (현재 시그니처는 `matchBanner(Long targetUserId)`)**

```java
@Transactional
public Optional<BannerResponse> matchBanner(Long targetUserId, String requestId) {
    // 1) 요청 ID 선점 (유니크 충돌이면 이미 처리된 요청)
    try {
        bannerRequestRepository.saveAndFlush(BannerRequest.create(requestId, targetUserId, LocalDateTime.now(clock)));
    } catch (DataIntegrityViolationException e) {
        BannerRequest prev = bannerRequestRepository.findById(requestId).orElseThrow();
        return rebuildResponse(prev.getNotificationId());   // 차감·기록 없이 같은 결과
    }
    // 2) 후보 선택·차감 (기존 로직 유지: BidAuction.pick, charge, deductBudget)
    // 3) 노출 기록 (ad_impressions), campaign_stats.sent_count +1
    // 4) outbox 행 추가 (payload = 3-2 형식)
    // 5) banner_requests 에 notification_id 기록 (후보 없으면 NULL로 둠)
}
```

- 후보가 없으면 `notification_id`는 NULL. 같은 요청 ID로 다시 오면 기본 배너(또는 204) 결과를 그대로 준다.
- 동시에 같은 요청 ID가 두 번 오면: 첫 번째 트랜잭션이 끝날 때까지 두 번째는 유니크 충돌에서 기다린다 → 충돌 후 조회로 기존 결과를 준다.
- `rebuildResponse`는 `ad_impressions`에서 `notification_id`로 노출 정보를 읽어 같은 응답을 만든다.
- `BidAuction.charge`는 현재 코드(2등 + 1원)를 그대로 쓴다. 바꾸지 않는다.

**(b) 릴레이 — `OutboxRelay`**

```java
@Scheduled(fixedDelayString = "${relay.outbox.interval-ms:1000}")
public void relay() {
    List<OutboxEvent> rows = outboxRepository.findTop500ByStatusOrderByOutboxIdAsc(PENDING);
    for (OutboxEvent row : rows) {
        eventPublisher.publish(AD_IMPRESSED, row.getCampaignId(), row.getPayload());  // .get() 으로 확인 대기
        outboxService.markPublished(row.getOutboxId());   // 별도 짧은 트랜잭션
    }
}
```

- 발행이 실패하면 예외를 기록하고 다음 주기에 다시 시도한다. 발행 완료 표시가 실패하면 중복 발행이 생기며, 재계산이 정리한다.
- 발행 완료 행은 하루 뒤 삭제하는 작업을 둔다 (`DELETE FROM outbox WHERE status='PUBLISHED' AND published_at < now() - interval '1 day'`).
- 한 번에 최대 500행. `campaign_id` 키로 발행하므로 같은 캠페인 순서가 파티션 안에서 유지된다.

### 5-2. DDL 전체 (`001_schema.sql`)


**MV 규칙 (담당 B가 지킬 것)**
- MV는 **새로 들어온 묶음만** 계산해서 대상 표에 더한다. 과거 데이터를 다시 계산하지 않는다.
- 분 표에서 시간·일 표를 만드는 MV는 **분 표에 행이 추가될 때** 실행된다. 재계산이 분 표를 교체해도 시간·일 표는 자동으로 바뀌지 않는다 → 재계산 SQL이 직접 교체한다 (5-3).
- 실시간 값에는 중복이 그대로 들어간다 (잠정). 중복 제거는 재계산에서만 한다.

### 5-3. 재계산 교체 SQL (담당 C가 실행, 내용은 담당 B가 확정)

> 날짜 `:d` (예: `2026-11-21`), S3 경로 `:glob` (예: `raw-clicks/2026/11/21/*/*.json`). 노출은 `raw-impressions/`로 같은 방식.

```sql
-- 1) 임시 표 비우기
TRUNCATE TABLE click_facts_stage;

-- 2) S3 원본 → 중복 제거 → 분·연령대·성별로 셈
INSERT INTO click_facts_stage
SELECT campaign_id, toStartOfMinute(event_at) AS minute, age_group, gender, count() AS cnt
FROM (
    SELECT notification_id,
           any(campaign_id) AS campaign_id,
           any(age_group)   AS age_group,
           any(gender)      AS gender,
           any(event_at)    AS event_at
    FROM s3('https://<RAW_S3_BUCKET>.s3.<RAW_S3_REGION>.amazonaws.com/raw-clicks/2026/11/21/*/*.json',
            'JSONEachRow',
            'notification_id String, campaign_id Int64, age_group String, gender String, event_at DateTime')
    GROUP BY notification_id
)
GROUP BY campaign_id, minute, age_group, gender;

-- 3) 분 표의 그 날짜 파티션 교체
ALTER TABLE click_facts REPLACE PARTITION 20261121 FROM click_facts_stage;

-- 4) 시간 표·일 표도 같은 날짜로 다시 만든 뒤 교체 (MV는 재실행되지 않음)
TRUNCATE TABLE click_facts_hour_stage;
INSERT INTO click_facts_hour_stage
SELECT campaign_id, toStartOfHour(minute) AS hour, age_group, gender, sum(cnt) AS cnt
FROM click_facts WHERE toDate(minute) = '2026-11-21'
GROUP BY campaign_id, hour, age_group, gender;
ALTER TABLE click_facts_hour REPLACE PARTITION 20261121 FROM click_facts_hour_stage;

TRUNCATE TABLE click_facts_day_stage;
INSERT INTO click_facts_day_stage
SELECT campaign_id, toDate(minute) AS day, age_group, gender, sum(cnt) AS cnt
FROM click_facts WHERE toDate(minute) = '2026-11-21'
GROUP BY campaign_id, day, age_group, gender;
ALTER TABLE click_facts_day REPLACE PARTITION 20261121 FROM click_facts_day_stage;
```

- 노출(`impression_facts*`)도 같은 4단계를 반복한다. 노출 S3 경로는 `raw-impressions/`.
- 한 날짜의 교체는 위 순서대로 한다. 중간에 실패하면 그 날짜를 처음부터 다시 실행한다 (멱등).
- 교체 전후 `SELECT sum(cnt)`로 행 수 변화를 `recompute_log`에 기록한다 (담당 C).

### 5-4. 조회 쿼리 (B-4)

> 실제 조회는 노출 표와 클릭 표를 따로 읽어 시각 기준으로 합친다. 두 표를 같은 시각 키로 `FULL OUTER JOIN` 하면 빈 구간이 0으로 채워진다. 예시 (시간 단위):

```sql
SELECT coalesce(i.bucket, c.bucket) AS bucket_start,
       coalesce(i.impression_count, 0) AS impression_count,
       coalesce(c.click_count, 0)      AS click_count
FROM (SELECT toStartOfHour(minute) AS bucket, sum(cnt) AS impression_count
      FROM impression_facts WHERE campaign_id = {id} AND minute >= {from} AND minute < {to}
      GROUP BY bucket) AS i
FULL OUTER JOIN
     (SELECT toStartOfHour(minute) AS bucket, sum(cnt) AS click_count
      FROM click_facts WHERE campaign_id = {id} AND minute >= {from} AND minute < {to}
      GROUP BY bucket) AS c
ON i.bucket = c.bucket
ORDER BY bucket_start;
```

- `granularity=day`이면 `toStartOfHour` 대신 `toDate`, 표는 `*_day`를 쓴다.
- 구간 수 800 이하 검사는 기존 Java 코드를 유지한다.
- **중요**: 응답의 `spentAmount`는 ClickHouse에 없다. 기존 `ad_impressions.charged_amount` 합계 (PostgreSQL)를 그대로 쓴다. 이 값은 B가 PostgreSQL 쿼리를 유지한다.
- 상위 N (`top-campaigns`): `click_facts` (분)에서 `[now - windowMinutes, now)` 구간을 캠페인별로 합산, 내 캠페인만(`@AdvertiserId`), 상위 `limit`개, 결과는 1분 캐시 없이 시작 (측정 뒤 캐시 검토).

### 6-2. S3 파일 규칙

- 경로: `raw-clicks/{yyyy}/{MM}/{dd}/{HH}/{batch_id}.json`, `raw-impressions/...` 같은 규칙.
- `{yyyy}/{MM}/{dd}/{HH}`는 **`event_at`** 기준 (처리 시각 아님).
- 한 파일 = JSON Lines (한 줄 = 메시지 1개, 줄 끝 `\n`).
- 파일을 닫는 기준: **1분 경과 또는 1,000줄**, 먼저 도달한 것.
- 한 파일에는 **한 토픽, 한 날짜(event_at 날짜)** 만 넣는다. 날짜가 다른 메시지가 섞이면 파일을 나눠서 닫는다.
- `batch_id`는 UUID.

### 6-3. 저장 컨슈머 (C-2)

```yaml
spring:
  kafka:
    consumer:
      group-id: raw-archive
      enable-auto-commit: false
      auto-offset-reset: earliest
      key-deserializer: org.apache.kafka.common.serialization.StringDeserializer
      value-deserializer: org.apache.kafka.common.serialization.StringDeserializer
    listener:
      ack-mode: manual
      concurrency: 3
```

```java
@KafkaListener(topics = {"ad-impressed", "ad-clicked"}, groupId = "raw-archive")
public void onMessage(ConsumerRecord<String, String> record, Acknowledgment ack) {
    rawBatchBuffer.add(record.topic(), record.value());   // 메모리에 쌓기
    if (rawBatchBuffer.shouldClose()) {                   // 1분 또는 1,000건
        rawBatchBuffer.closeAndUpload();                  // S3 업로드 + raw_archive_batch 기록 (한 트랜잭션 아님: 아래 설명)
        ack.acknowledge();                                // 업로드 성공 후에만 커밋
    }
}
```

- 커밋은 **배치를 S3에 올린 뒤에만** 한다. 중간에 죽으면 마지막 커밋 위치부터 다시 읽어서 같은 메시지를 다시 쓴다 → 재계산이 정리한다.
- `raw_archive_batch` 기록은 S3 업로드 **성공 후** 한다. 기록에 실패해도 파일은 남는다 (조정이 파일 수와 비교해 찾는다).
- 토픽별로 버퍼를 나눈다 (노출과 클릭을 한 파일에 섞지 않는다).
- 1분 타이머는 별도 스레드 또는 `@Scheduled(fixedDelay=5000)` 로 버퍼를 확인한다. 메시지가 없어도 1분이 지나면 닫는다.
- 종료 시 (`@PreDestroy`) 남은 버퍼를 닫고 커밋한다.

### 6-4. 재계산 작업 (C-5)

- **실행 시각**: 매일 03:00 (`recompute.cron`).
- **대상 날짜**: `어제`, `그저께` (`recompute.window-days = 2`). 두 날짜를 **순서대로** 처리한다 (병렬 금지).
- **날짜마다**:
  1. `recompute_log`에 `RUNNING` 행 삽입
  2. ClickHouse에 5-3의 SQL 실행 (클릭, 노출 각각, 분·시간·일)
  3. 결과 행 수와 중복 제거 수를 `recompute_log`에 기록
  4. 성공이면 `SUCCESS`, 예외면 `FAILED` + `error_message`
- 실패하면 **1회 재시도** 후 `FAILED`로 남기고 다음 날짜로 넘어간다. 실패는 경고 로그를 남긴다.
- 수동 실행: `--recompute.from=2026-11-20 --recompute.to=2026-11-21` (C-7).
- 같은 날짜를 두 번 실행해도 결과가 같다 (교체 방식).

### 6-5. 조정 작업 (C-6)

매일 03:30, 대상 날짜마다 아래를 계산하고 `recompute_log`에 쓴다.

| 항목 | 값 | 계산 방법 |
|---|---|---|
| `kafka_read_count` | 클릭 + 노출 | `SELECT sum(consumed_count) FROM raw_archive_batch WHERE event_date = :d` |
| `s3_line_count` | 클릭 + 노출 | `SELECT sum(written_count) FROM raw_archive_batch WHERE event_date = :d` |
| `s3_unique_count` | 클릭 + 노출 | ClickHouse: `SELECT uniqExact(notification_id) FROM s3('.../raw-clicks/.../*.json', ...)` + 노출 같은 방식 |
| `ch_daily_count` | 클릭 + 노출 | ClickHouse: `SELECT sum(cnt) FROM click_facts WHERE toDate(minute) = :d` (+ 노출) |
| `pg_impression_count` | 노출 | PostgreSQL: `SELECT count(*) FROM ad_impressions WHERE shown_at >= :d AND shown_at < :d+1` |

판정 (`reconcile_ok`):

1. `kafka_read_count = s3_line_count` (저장 단계 확인)
2. `s3_unique_count = ch_daily_count` (재계산·교체 확인)
3. 노출만: `pg_impression_count = s3_unique_count(노출)` (노출 발행 확인)

- 셋 다 맞으면 `reconcile_ok = true`. 하나라도 다르면 `false`와 어떤 항목인지 `error_message`에 적고 **경고 로그**. 자동 재계산은 하지 않는다.
- 조정은 재계산 **뒤에** 실행된다 (03:00 → 03:30). 재계산이 `FAILED`였던 날짜는 조정도 `false`로 기록한다.

> 주의: 3번 판정은 **하루 뒤 그 날짜의 노출이 모두 발행된 뒤**에만 맞는다. 릴레이가 밀리면 `pg_impression_count`가 더 크게 나온다. 이때는 경고로 남기고, 다음 날 다시 맞는지 본다.

### 6-6. 스케줄러 설정

```java
@Scheduled(cron = "${recompute.cron:0 0 3 * * *}")   // RecomputeJob
@Scheduled(cron = "${reconcile.cron:0 30 3 * * *}")  // ReconcileJob
```

- 두 작업은 같은 프로세스에서 돌아도 된다 (모놀리식). 동시에 실행되지 않도록 03:00 작업이 끝나야 03:30이 돈다 (시각 차이로 보장).
