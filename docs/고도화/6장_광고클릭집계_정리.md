# 0. 먼저 알아둘 단어

| 단어 | 뜻 |
|---|---|
| 광고 클릭 이벤트 | 사용자가 광고를 한 번 누를 때마다 생기는 기록 한 줄 |
| 집계(aggregation) | 흩어진 기록을 세어서 묶는 것. 예: 광고 A가 1분 동안 몇 번 눌렸는지 세기 |
| 로그 | 시스템이 일어난 일을 파일이나 줄 단위로 남기는 기록 |
| RTB (Real-Time Bidding, 실시간 경매) | 광고 노출 자리를 사람이 보는 순간 경매로 사고파는 방식 |
| DSP (Demand-Side Platform) | 광고주 쪽에서 광고를 사고 입찰하는 플랫폼 |
| SSP (Supply-Side Platform) | 지면(광고 칸)을 가진 쪽에서 팔고 내놓는 플랫폼 |
| 광고 거래소 | DSP와 SSP를 이어 주는 경매 장소 |
| CTR (Click-Through Rate, 클릭률) | 노출된 횟수 대비 클릭된 비율 |
| CVR (Conversion Rate, 전환률) | 클릭한 사람 중 실제 구매 같은 목표 행동을 한 비율 |
| QPS (Queries Per Second) | 1초에 처리하는 요청 수 |
| 원시 데이터(raw data) | 가공하지 않은 클릭 기록 그대로 |
| 집계 결과 데이터 | 원시 데이터를 세어서 만든 요약 숫자 |
| 메시지 큐 | 보내는 쪽과 받는 쪽 사이에서 데이터를 줄 세워 잠시 쌓아 두는 중간 통로 (예: 카프카) |
| 원자적 커밋 (atomic commit) | 여러 작업을 한 덩어리로 묶어서 전부 성공하거나 전부 실패하게 하는 것 |
| 정확히 한 번 (exactly once) | 같은 데이터가 중복 없이, 빠짐 없이 딱 한 번만 처리되는 것 |
| DAG (Directed Acyclic Graph) | 방향이 있고 되돌아오는 고리가 없는 작업 흐름도 |
| 맵(map) / 리듀스(reduce) | 맵은 나눠서 갈라 보내기, 리듀스는 모아서 합치기 |
| 스타 스키마 (star schema) | 집계 기준(국가, 기기 등)을 미리 나눠서 저장하는 표 설계 방식 |
| 차원 (dimension) | 필터링에 쓰이는 기준 필드. 예: 국가, 지역 |
| 시계열 데이터 | 시간 순서대로 쌓이는 데이터. 예: 1분마다 기록되는 클릭 수 |
| 콜드 스토리지 (cold storage) | 자주 쓰지 않는 데이터를 싸고 느린 저장소에 옮겨 두는 것 |
| 람다 아키텍처 (lambda) | 실시간 처리 경로와 일괄 처리 경로를 둘 다 두는 구조 |
| 카파 아키텍처 (kappa) | 스트리밍 엔진 하나로 실시간 처리와 재처리를 모두 해결하는 구조 |
| 이벤트 시각 (event time) | 광고 클릭이 실제로 발생한 시각 |
| 처리 시각 (processing time) | 집계 서버가 그 클릭을 처리한 시각 |
| 워터마크 (watermark) | "이 시각보다 이전 이벤트는 더 이상 안 온다"고 정해 집계 구간을 닫는 기준 시각 |
| 텀블링 윈도우 (tumbling window) | 서로 겹치지 않고 같은 길이로 끊어지는 시간 구간 (예: 1분씩) |
| 슬라이딩 윈도우 (sliding window) | 시간 구간을 조금씩 밀고 가며, 구간끼리 겹칠 수 있음 |
| 전달 보장 (delivery guarantee) | 메시지가 몇 번 전달되는지 보장하는 수준 |
| 최대 한 번 / 최소 한 번 / 정확히 한 번 | 전달 보장의 세 가지 수준 (3단계 본문에서 자세히 설명) |
| 오프셋 (offset) | 카프카에서 "어디까지 읽었는지"를 나타내는 위치 번호 |
| 분산 트랜잭션 (distributed transaction) | 여러 컴퓨터에서 돌아가는 작업을 한 덩어리로 묶어, 하나라도 실패하면 모두 되돌리는 방식 |
| 중복 제거 (deduplication) | 같은 이벤트가 두 번 집계되지 않도록 걸러내는 일 |
| 스냅숏 (snapshot) | 시스템의 특정 시점 상태를 저장해 둔 것. 장애 복구에 씀 |
| 조정 (reconciliation) | 서로 다른 두 결과를 비교해서 맞는지 확인하는 일 |
| 핫스팟 (hotspot) | 다른 서버보다 유독 많은 데이터를 받는 노드나 샤드 |
| 자원 관리자 (resource manager) | 서버 자원(CPU, 메모리)을 나눠 주는 관리 프로그램. 예: YARN |
| 가상 노드 (virtual node) | 한 대의 실제 서버 안에서 여러 개의 작은 담당 구역을 둘 수 있게 한 것 |

# 1. 이 장이 다루는 것

- 페이스북, 유튜브, 틱톡 같은 온라인 미디어가 커지면서 디지털 광고가 전체 광고 매출에서 차지하는 비중이 계속 커지고 있습니다.
- 그래서 광고 클릭을 세고 기록하는 일의 중요성도 커졌습니다. 이 장은 페이스북이나 구글 규모의 **광고 클릭 이벤트 집계 시스템**을 설계합니다.
- 온라인 광고의 큰 장점은 **실시간 데이터로 광고 효과를 숫자로 잴 수 있다**는 점입니다.

## 1-1. 광고가 나가는 전체 흐름 (RTB)

```
[광고주]  ->  [DSP 수요자 플랫폼]  ->  [광고 거래소]  ->  [SSP 공급자 플랫폼]  ->  [공급자 (지면)]
```

- 광고주는 DSP를 통해 "이 사용자에게 광고를 보여주고 싶다"고 입찰합니다.
- 광고 거래소가 경매를 열고, 이긴 광고가 지면에 나갑니다.
- 이 과정은 보통 **1초 안**에 끝나야 합니다.

## 1-2. 왜 집계가 중요한가

- 집계 데이터는 광고주가 광고 효율을 판단하는 근거입니다.
- 캠페인 관리자는 이 데이터를 보고 예산을 늘리거나 줄이고, 타겟 그룹이나 키워드를 바꿉니다.
- 광고 과금도 집계된 클릭 수를 기준으로 합니다. 그래서 **정확성**이 특히 중요합니다.
- 대표 지표는 CTR(클릭률)과 CVR(전환률)이며, 둘 다 집계된 클릭 데이터로 계산합니다.

# 2. 1단계: 문제 이해와 설계 범위 정하기

설계를 시작하기 전에 "무엇을, 얼마나 크게 만들지"를 먼저 정합니다. 책에서는 면접관에게 질문하는 형식으로 정리합니다.

## 2-1. 질문과 답

| 질문 | 답 |
|---|---|
| 입력 데이터는 어떤 형태인가? | 여러 서버에 흩어진 **로그 파일**입니다. 클릭이 일어날 때마다 로그 파일 끝에 한 줄씩 추가됩니다. |
| 클릭 기록에는 무엇이 들어 있나? | `ad_id`(광고 번호), `click_timestamp`(클릭 시각), `user_id`(사용자 번호), `ip`(접속 주소), `country`(국가) 등 |
| 데이터는 얼마나 많은가? | 하루 클릭 **10억 건**, 광고 **200만 개**. 클릭 수는 해마다 **30%씩** 늘어난다고 가정합니다. |
| 가장 중요하게 지원해야 할 질의는? | 아래 3가지 |

**가장 중요한 질의 3가지**

1. **특정 광고의 지난 M분 동안의 클릭 수**
2. **지난 1분 동안 가장 많이 클릭된 광고 100개**
   - 질의 기간(M분)과 광고 개수(100)는 바꿀 수 있어야 합니다.
   - 집계는 **매분** 이루어집니다.
3. **ip, user_id, country 같은 속성으로 위 1번과 2번 결과를 걸러서 보기**

> 참고: 책 원문에 광고 수가 한 곳은 "2백만 회 게재", 다른 곳은 "200만 개"로 적혀 있습니다. 둘 다 "광고 200만 개"로 이해하면 됩니다.

## 2-2. 조심해야 할 특이 상황 (엣지 케이스)

엣지 케이스는 "평소엔 잘 안 일어나지만 일어나면 문제가 되는 상황"입니다.

- **예상보다 늦게 도착하는 이벤트**가 있을 수 있습니다. 네트워크가 느려서 클릭 기록이 늦게 들어오는 경우입니다.
- **중복된 이벤트**가 들어올 수 있습니다. 같은 클릭이 두 번 기록되면 집계가 틀어집니다.
- **시스템 일부가 언제든 다운될 수 있습니다.** 그래서 복구 방법도 생각해야 합니다.

## 2-3. 지연 시간 (얼마나 늦어도 되는가)

| 처리 | 허용 시간 | 이유 |
|---|---|---|
| RTB (광고 경매) | **1초 미만** | 사용자 화면이 바로 바뀌어야 하기 때문 |
| 광고 클릭 집계 | **몇 분 이내** | 과금과 보고서에 쓰이므로 약간 늦어도 괜찮음 |

> 중요: 이 시스템은 RTB처럼 빨라야 하는 것이 아니라, **몇 분 안에만 끝나면 되는** 시스템입니다.

## 2-4. 기능 요구사항 (시스템이 해야 할 일)

1. 지난 M분 동안의 `ad_id`별 클릭 수를 집계한다.
2. 매분 가장 많이 클릭된 상위 100개 광고 ID를 돌려준다.
3. 여러 속성(국가, 기기 등)을 기준으로 집계 결과를 걸러서 볼 수 있다.
4. 데이터 양은 페이스북이나 구글 규모다. (아래 개략 계산 참고)

## 2-5. 비기능 요구사항 (잘 해야 하는 품질)

| 항목 | 뜻 | 이 시스템에서 왜 중요한가 |
|---|---|---|
| 정확성 | 집계 숫자가 맞아야 함 | RTB와 광고 과금에 직접 쓰임 |
| 중복·지연 처리 | 늦게 오거나 두 번 온 이벤트를 제대로 다뤄야 함 | 숫자가 틀어지는 주된 원인 |
| 견고성 (reliability) | 일부가 고장 나도 버텨야 함 | 서버는 언제든 죽을 수 있음 |
| 지연 시간 | 전체 처리는 최대 몇 분 | 대시보드가 너무 늦으면 의미가 없음 |

## 2-6. 개략 계산 (규모 가늠하기)

설계 전에 "대략 얼마나 큰 시스템인가"를 숫자로 잡습니다. 아래 가정은 책에서 정한 값입니다.

| 항목 | 계산 | 결과 |
|---|---|---|
| 하루 능동 사용자 (DAU) | 가정 | 10억 명 |
| 하루 클릭 수 | 사용자 1명이 하루 평균 광고 1개 클릭 | 10억 건 |
| 평균 QPS | 10⁹ ÷ 10⁵초 (하루를 약 10만 초로 어림) | **10,000** |
| 최대 QPS | 평균의 5배로 가정 | **50,000** |
| 클릭 1건 저장 크기 | 가정 | 0.1KB |
| 하루 저장 용량 | 0.1KB × 10억 | 약 **100GB** |
| 한 달 저장 용량 | 하루 100GB × 30일 | 약 **3TB** |

- 쓰기(클릭 기록)가 초당 최대 5만 번 들어올 수 있으므로, 쓰기를 잘 처리하는 구조가 필요합니다.
- 한 달 3TB는 한 대의 작은 서버에 담기 어려운 크기입니다.

# 3. 2단계: 개략 설계안 제시 및 동의 구하기

## 3-1. 질의 API 설계

### 왜 API가 필요한가

- **API**는 클라이언트(요청하는 쪽)와 서버(응답하는 쪽)가 주고받을 **약속된 요청 형식**입니다.
- 이 시스템의 클라이언트는 일반 앱 사용자가 아닙니다. **대시보드를 보는 데이터 과학자, 제품 관리자, 광고주**입니다.
- 앞의 기능 요구사항 3개는 **API 2개**로 모두 지원할 수 있습니다. 필터 기능은 **호출할 때 넘기는 인자(파라미터)**로 처리합니다.

### API 1: 지난 M분 동안 각 광고의 클릭 수

- **주소**: `GET /v1/ads/{ad_id}/aggregated_count`
- **용도**: 광고 하나의 최근 클릭 수를 알려 줍니다.

**요청 인자**

| 인자 이름 | 뜻 | 자료형 | 기본값 |
|---|---|---|---|
| `from` | 집계 시작 시각 | long | 지금부터 1분 전 |
| `to` | 집계 종료 시각 | long | 지금 |
| `filter` | 걸러낼 기준의 번호. 예: `filter=001`이면 미국 이외 지역 클릭을 뺌 | long | 없음 |

**응답**

| 필드 이름 | 뜻 | 자료형 |
|---|---|---|
| `ad_id` | 광고 번호 | string |
| `count` | 집계된 클릭 횟수 | long |

### API 2: 지난 M분 동안 클릭이 가장 많은 상위 N개 광고

- **주소**: `GET /v1/ads/popular_ads`
- **용도**: 지금 가장 많이 클릭된 광고 목록을 알려 줍니다.

**요청 인자**

| 인자 이름 | 뜻 | 자료형 |
|---|---|---|
| `count` | 상위 몇 개를 돌려줄지 (예: 100) | integer |
| `window` | 집계할 시간 범위, 분 단위 (예: 1) | long |
| `filter` | 걸러낼 기준의 번호 | integer |

**응답**

| 필드 이름 | 뜻 | 자료형 |
|---|---|---|
| `ad_ids` | 광고 번호들의 목록 | array (배열) |

> 용어: **array(배열)**는 여러 값을 순서대로 담은 목록입니다. 예: `["ad3", "ad1", "ad2"]`

## 3-2. 데이터 모델: 어떤 데이터를 어떤 모양으로 저장하나

이 시스템이 다루는 데이터는 두 종류입니다.

- **원시 데이터**: 클릭 기록 한 줄 한 줄
- **집계 결과 데이터**: 원시 데이터를 세어서 만든 요약

### 원시 데이터 (클릭 기록 원본)

로그 파일에 찍히는 한 줄의 예는 이렇습니다.

```
[AdClickEvent] ad001, 2021-01-01 00:00:01, user 1, 207.148.22.22, USA
```

이 한 줄을 표로 바꾸면 다음과 같습니다.

| ad_id | click_timestamp | user_id | ip | country |
|---|---|---|---|---|
| ad001 | 2021-01-01 00:00:01 | user1 | 207.148.22.22 | USA |
| ad001 | 2021-01-01 00:00:02 | user1 | 207.148.22.22 | USA |
| ad002 | 2021-01-01 00:00:02 | user2 | 209.153.56.11 | USA |

- 이 기록은 여러 **애플리케이션 서버**에 흩어져 있습니다. 한곳에 모여 있지 않습니다.

### 집계 결과 데이터 (세어서 만든 숫자)

**분 단위 집계 (책 표 6.8)**

| ad_id | click_minute | count |
|---|---|---|
| ad001 | 202101010000 | 5 |
| ad001 | 202101010001 | 7 |

- `click_minute`는 `202101010000`처럼 **연·월·일·시·분**을 이어 붙인 숫자입니다. 2021년 1월 1일 00시 00분을 뜻합니다.
- 즉 "ad001은 00시 00분에 5번, 00시 01분에 7번 눌렸다"는 뜻입니다.

**필터를 넣은 집계 (책 표 6.9)**

필터링을 하려면 `filter_id` 열을 추가합니다. 같은 광고, 같은 분이라도 필터 기준이 다르면 숫자가 달라집니다.

| ad_id | click_minute | filter_id | count |
|---|---|---|---|
| ad001 | 202101010000 | 0012 | 2 |
| ad001 | 202101010000 | 0023 | 3 |
| ad001 | 202101010001 | 0012 | 1 |
| ad001 | 202101010001 | 0023 | 6 |

**필터 기준 표 (책 표 6.10)**

| filter_id | region (지역) | ip | user_id |
|---|---|---|---|
| 0012 | US | 0012 | * |
| 0013 | * | 0023 | 123.1.2.3 |

- `*`는 "전체"라는 뜻입니다. 예를 들어 0012는 "지역이 US인 것"을 골라냅니다.

**상위 광고 목록 표 (책 표 6.11, `most_clicked_ads`)**

| 열 이름 | 자료형 | 뜻 |
|---|---|---|
| `window_size` | integer | 집계한 시간 범위 (분) |
| `update_time_minute` | timestamp | 마지막으로 갱신한 시각 (1분 단위) |
| `most_clicked_ads` | array | 상위 광고 번호 목록 (JSON 형식으로 저장) |

> 용어: **JSON**은 `{"키": 값}` 모양으로 데이터를 적는 표준 글자 형식입니다.

### 원시 데이터와 집계 데이터, 무엇을 저장할까?

| | 원시 데이터만 저장 | 집계 결과만 저장 |
|---|---|---|
| 장점 | 원본이 그대로 남음. 필터와 재계산이 가능 | 용량이 작음. 질의가 빠름 |
| 단점 | 용량이 엄청남. 질의가 느림 | 원본이 없어서 계산이 틀어졌을 때 되돌릴 수 없음 |

**결론: 둘 다 저장합니다.** 이유는 다음과 같습니다.

1. **문제가 생겼을 때 원인을 찾으려면 원본이 필요합니다.** 버그로 집계가 깨지면 원시 데이터에서 다시 계산할 수 있습니다.
2. **원시 데이터를 직접 질의하면 너무 느립니다.** 평소 질의는 집계 결과에 합니다.
3. **원시 데이터는 백업 용도입니다.** 재계산할 때가 아니면 매일 꺼내 볼 일이 없습니다. 오래된 원시 데이터는 **콜드 스토리지**로 옮기면 비용을 줄일 수 있습니다.
4. **집계 결과는 자주 읽히는 "활성 데이터"입니다.** 질의가 빠르도록 튜닝해서 둡니다.

### 데이터베이스 선택 기준

데이터베이스를 고를 때 책이 던지는 질문은 4가지입니다.

1. 데이터가 어떤 모양인가? (관계형 표 / 문서 / 이진 대형 객체 BLOB)
2. 읽기가 중요한가, 쓰기가 중요한가, 둘 다인가?
3. 트랜잭션(여러 작업을 한 묶음으로 처리)이 필요한가?
4. 합계(SUM)나 개수(COUNT) 같은 집계 함수를 많이 쓰는가? (이를 OLAP 함수라고 함)

**원시 데이터 저장소**

- 원시 데이터는 **쓰기 중심**이고, 읽기는 거의 없습니다. 평균 쓰기는 초당 1만 건, 최대는 5만 건입니다.
- 관계형 DB로도 가능하지만, 이 규모의 쓰기를 감당하도록 구성하기가 어렵습니다.
- 그래서 **카산드라(Cassandra)** 또는 **InfluxDB**처럼 쓰기와 시간 범위 조회에 강한 DB가 더 적합합니다.
- 대안으로 ORC, Parquet, AVRO 같은 **컬럼형 파일 형식**을 쓰고 S3에 저장하는 방법도 있습니다. 파일 크기 제한을 두고 넘으면 새 파일을 만드는 식입니다. 다만 구성이 복잡하기 때문에 이 설계에서는 카산드라를 씁니다.

**집계 결과 저장소**

- 집계 결과는 **시계열 데이터**입니다. 시간 순서대로 1분마다 쌓입니다.
- 매분 기록하고, 대시보드가 계속 읽어 갑니다. 광고가 200만 개라서 읽기도 많습니다.
- 원시 데이터와 같은 종류의 DB를 써도 괜찮습니다.

## 3-3. 개략 설계

### 데이터가 흐르는 순서

```
[로그 모니터]
     |
     v
[메시지 큐 1]  ----------------------------->  [데이터베이스 기록 프로세스]  ----->  [원시 데이터 DB]
     |
     v
[데이터 집계 서비스]
     |  (1) 광고별 클릭 수, 매분
     |  (2) 상위 100개 광고, 매분
     v
[메시지 큐 2]
     |
     v
[데이터베이스 기록 프로세스]  ----->  [집계 결과 DB]  <-----  [질의 서비스 (대시보드)]
```

| 부품 | 하는 일 |
|---|---|
| 로그 모니터 (watcher) | 로그 파일에 새 클릭이 생겼는지 보다가, 생기면 메시지 큐로 보냄 |
| 메시지 큐 1 | 원시 클릭 기록을 잠시 쌓아 둠 |
| 데이터베이스 기록 프로세스 | 큐에서 꺼내서 DB가 읽을 수 있는 모양으로 바꿔 저장 |
| 원시 데이터 DB | 클릭 기록 원본 보관 |
| 데이터 집계 서비스 | 클릭을 세서 매분 집계 결과를 만듦 |
| 메시지 큐 2 | 집계 결과를 잠시 쌓아 둠 |
| 집계 결과 DB | 집계 숫자를 보관 |
| 질의 서비스 | 대시보드의 요청을 받아 집계 결과 DB를 읽어 응답 |

### 왜 중간에 메시지 큐를 넣나? (동기와 비동기)

**동기 방식**: 한 단계가 끝날 때까지 다음 단계가 기다리는 방식입니다.
- 문제 1: 클릭이 갑자기 많아지면, 받는 쪽이 감당하지 못해 메모리가 부족해질 수 있습니다.
- 문제 2: 한 부품이 죽으면 전체가 멈춥니다.

**비동기 방식 (메시지 큐 사용)**: 보내는 쪽이 큐에 넣고 바로 다음 일을 하고, 받는 쪽은 자기 속도대로 꺼내 씁니다.
- 생산자(클릭을 보내는 쪽)와 소비자(집계하는 쪽)가 **서로 독립적으로 늘어나고 줄어들 수 있습니다.**
- 한쪽이 잠깐 느려도 큐가 완충 역할을 합니다.

> 이 장에서 메시지 큐의 대표 예시는 **카프카(Kafka)**입니다.

### 메시지 큐 1에 들어가는 데이터

로그 모니터가 큐 1에 넣는 것은 **클릭 기록 원본 한 건**입니다.

| ad_id | click_timestamp | user_id | ip | country |
|---|---|---|---|---|

### 메시지 큐 2에 들어가는 데이터

집계 서비스가 큐 2에 넣는 것은 **집계 결과 두 종류**입니다.

**종류 1: 분 단위 광고 클릭 수**

| ad_id | click_minute | count |
|---|---|---|

**종류 2: 분 단위 상위 N개 광고 목록**

| update_time_minute | most_clicked_ads |
|---|---|

### 왜 집계 결과를 바로 DB에 쓰지 않고 큐 2를 거치나?

- 목표는 **정확히 한 번(exactly once)** 처리입니다. 같은 집계가 두 번 저장되거나, 중간에 일부만 저장되면 안 됩니다.
- 이를 위해 **원자적 커밋**이 필요합니다. 쉽게 말해 "저장이 전부 되었거나, 전부 안 된 것" 둘 중 하나만 있게 하는 장치입니다.
- 카프카 같은 메시지 큐는 이 보장을 돕기 때문에 두 번째 큐로 넣습니다 (그림 6.4).
- 책의 그림 6.4에서 점선 상자는 "로그 모니터부터 메시지 큐 2까지"를 **원자적으로 처리하는 범위**를 보여 줍니다.

## 3-4. 집계 서비스 안쪽 (MapReduce, DAG)

### 왜 MapReduce인가

- 클릭 데이터는 너무 많아서 **서버 한 대로는 셀 수 없습니다.**
- 그래서 데이터를 여러 서버에 나눠 세고, 마지막에 합치는 **MapReduce(맵리듀스)** 방식을 씁니다.
- 이 방식의 작업 순서를 그림으로 나타낸 것이 **DAG(방향 비순환 그래프)**입니다. 쉽게 말해 "화살표 방향으로만 흘러가는 작업 순서도"입니다.

### 세 종류의 노드

작업을 아주 작은 단위로 쪼갠 것을 **노드**라고 합니다. 각 노드는 한 가지 일만 하고, 결과를 다음 노드로 넘깁니다.

| 노드 | 하는 일 | 쉬운 말로 |
|---|---|---|
| 맵 노드 (map) | 입력을 걸러내고 바꿔서 여러 갈래로 나눠 보냄 | 택배를 지역별로 분류하기 |
| 집계 노드 (aggregate) | 받은 데이터를 광고별로 세기 | 분류된 택배 개수 세기 |
| 리듀스 노드 (reduce) | 여러 집계 결과를 합쳐서 최종 답을 냄 | 각 지역 개수를 모아 전체 순위 매기기 |

> 주의: 여기서 쓴 "택배" 같은 비유는 이해를 돕는 용도일 뿐이고, 실제 시스템의 이름과 다를 수 있습니다. 실제 역할은 위 표의 설명을 기준으로 보세요.

### 맵 노드 예시

책의 예: 맵 노드가 `ad_id % 2 = 0` 조건을 확인합니다.

- `%`는 **나머지 연산**입니다. `ad_id % 2`는 2로 나눈 나머지를 뜻합니다.
- 나머지가 0이면 → 집계 노드 1로 보냅니다.
- 나머지가 1이면 → 집계 노드 2로 보냅니다.

```
입력 데이터 --> [분배 (맵)] --(ad_id % 2 = 0)--> [집계 노드 1]
                           --(ad_id % 2 = 1)--> [집계 노드 2]
```

### 맵 노드는 꼭 필요한가?

- 카프카의 파티션(칸막이)이나 태그를 나눠서, 집계 노드가 카프카를 **바로 읽게** 할 수도 있습니다. 이 방법도 동작은 합니다.
- 하지만 **입력 데이터를 정리하거나 정규화(같은 모양으로 맞추기)** 해야 할 때는 맵 노드가 있어야 편합니다.
- 또 다른 이유: 데이터를 만드는 쪽을 우리가 통제할 수 없으면, **같은 광고 번호의 클릭이 서로 다른 카프카 파티션에 들어갈 수 있습니다.** 맵 노드가 같은 광고 번호를 한곳으로 모아 줍니다.

### 집계 노드

- 집계 노드는 광고 번호별 클릭 수를 **메모리(RAM) 안에서** 매분 셉니다.
- 실제 집계 노드는 **리듀스 과정의 일부**입니다. 그래서 전체 흐름을 줄이면 "맵 → 집계 → 리듀스"가 실제로는 "맵 → 리듀스 → 리듀스"로 보이는 것입니다.

### 리듀스 노드 예시 (책 그림 6.7)

집계 노드 3개가 각자 센 결과입니다.

| 집계 노드 | 광고별 클릭 수 |
|---|---|
| 노드 A | ad1: 12, ad3: 5, ad2: 3 |
| 노드 B | ad7: 9, ad10: 4, ad8: 3 |
| 노드 C | ad13: 8, ad11: 4, ad15: 3 |

- 각 집계 노드는 자기 안에서 **상위 3개**만 골라 리듀스 노드로 보냅니다.
- 리듀스 노드는 받은 9개 중에서 최종 **상위 3개**를 고릅니다.
- 결과: **ad1 (12), ad7 (9), ad13 (8)**

### 노드끼리 어떻게 주고받나

| 노드가 어디에 있는가 | 주고받는 방법 |
|---|---|
| 서로 다른 **프로세스** (다른 프로그램) | **TCP** (네트워크 통신) |
| 서로 다른 **스레드** (같은 프로그램 안의 일꾼) | **공유 메모리** (같은 메모리 칸을 같이 씀) |

- 노드의 중간 결과는 **메모리에 저장**해 둘 수 있습니다. 그래서 빠릅니다.

### 실제로 지원하는 사용 사례 3가지

**사례 1: 광고별 클릭 수 집계 (책 그림 6.8)**
- 맵 노드가 `ad_id % 3`으로 이벤트를 집계 노드 3개에 나눠 보냅니다.
- 각 집계 노드가 자기 몫을 셉니다.
- 예시 결과: 지난 1분 동안 ad3는 4번, ad1은 3번, ad2는 5번 클릭되었습니다.

**사례 2: 가장 많이 클릭된 상위 N개 광고 (책 그림 6.9, 상위 3개 예)**
- 집계 노드 3개가 각자 상위 3개를 뽑습니다. 합계 9개입니다.
- 리듀스 노드가 9개 중 상위 3개를 고릅니다. 예: ad3 (12), ad1 (9), ad2 (8).
- N이 100이어도 같은 방식으로 늘릴 수 있습니다.

**사례 3: 데이터 필터링 (책 표 6.16)**
- 필터 기준을 미리 정해 두고, 그 기준으로 나눠서 셉니다. 예: 국가별로 USA, GPB, others로 나눕니다.
- 같은 광고라도 국가에 따라 따로 셉니다.

| ad_id | click_minute | country | count |
|---|---|---|---|
| ad001 | 202101010001 | USA | 100 |
| ad001 | 202101010001 | GPB | 200 |
| ad001 | 202101010001 | others | 3000 |
| ad002 | 202101010001 | USA | 10 |
| ad002 | 202101010001 | GPB | 25 |
| ad002 | 202101010001 | others | 12 |

### 스타 스키마: 필터 방식의 이름과 장단점

- 이런 방식을 **스타 스키마(star schema)**라고 합니다. 데이터 웨어하우스(분석용 대형 저장소)에서 많이 쓰는 방식입니다.
- 필터에 쓰는 기준 열(국가, 지역 등)을 **차원(dimension)**이라고 부릅니다.

| 장점 | 한계 |
|---|---|
| 이해하기 쉽고 만들기 간단함 | 기준이 많아질수록 **버킷(칸)과 레코드가 엄청 많이 생김** |
| 기존 집계 서비스를 그대로 써서 차원을 더 늘릴 수 있음 | |
| 추가 부품이 필요 없음 | |
| 결과를 미리 계산해 둬서 필터 조회가 빠름 | |

## 4-1. 스트리밍 vs 일괄 처리

### 세 가지 시스템 비교 (책 표 6.17)

| 구분 | 서비스 (온라인 시스템) | 일괄 처리 (오프라인) | 스트리밍 (실시간에 가깝게) |
|---|---|---|---|
| 응답성 | 클라이언트에게 빠르게 응답 | 클라이언트에 응답할 필요 없음 | 클라이언트에 응답할 필요 없음 |
| 입력 | 사용자의 요청 | 유한한 크기의 입력, 큰 규모 데이터 | 경계가 없는 입력 (무한 스트림) |
| 출력 | 클라이언트에 대한 응답 | 구체화 뷰, 집계 결과, 지표 등 | 구체화 뷰, 집계 결과, 지표 등 |
| 성능 측정 기준 | 가용성, 지연 시간 | 처리량 | 처리량, 지연 시간 |
| 사례 | 온라인 쇼핑 | 맵리듀스 | 플링크(Flink) |

- 이 설계는 **스트리밍과 일괄을 둘 다 사용**합니다.
  - 스트리밍: 데이터를 들어오는 대로 처리해서 거의 실시간 집계 결과를 만듭니다.
  - 일괄: 이력 데이터를 백업하고 다시 계산하는 데 씁니다.
- 이 두 경로를 동시에 지원하는 구조를 **람다 아키텍처(lambda)**라고 합니다.
  - 장점: 실시간과 정확성을 둘 다 챙길 수 있습니다.
  - 단점: **같은 로직을 두 벌(실시간용, 일괄용)로 만들어 관리해야 합니다.** 코드가 두 벌이 되는 것이 가장 큰 불편입니다.

### 카파 아키텍처 (책 그림 6.10)

- **카파 아키텍처(kappa)**는 일괄 처리와 스트리밍 처리 경로를 **하나로 합칩니다.**
- 핵심 아이디어: **스트리밍 엔진 하나**로 실시간 처리와 끊임없는 재처리 문제를 모두 해결합니다.
- 이 설계안은 카파 아키텍처를 따릅니다. 그래서 **이력 데이터의 재처리도 실시간 집계 서비스를 거칩니다.** 자세한 내용은 아래 "데이터 재계산"에서 다룹니다.

## 4-2. 데이터 재계산 (이력 데이터 재처리)

### 왜 필요한가

- 이미 집계한 데이터를 다시 계산해야 하는 경우가 있습니다. 이를 **이력 데이터 재처리(historical data replay)**라고 합니다.
- 예: 집계 서비스에 중대한 버그가 있었다고 합시다. 버그가 생긴 시점부터 원시 데이터를 다시 읽어서 집계 결과를 **재계산**하고 고쳐야 합니다.

### 재계산 흐름 (책 그림 6.11)

1. **재계산 서비스가 원시 데이터 저장소에서 데이터를 검색**합니다. 일괄 처리 방식입니다.
2. 꺼낸 데이터는 **재계산 전용 집계 서비스**로 보냅니다.
3. 집계 결과는 **두 번째 메시지 큐**로 보내져서, 집계 결과 DB에 반영됩니다.

### 왜 전용 집계 서비스를 따로 두나

- 재계산은 **집계 로직은 재사용하지만**, 처리할 데이터는 **다른 곳에서 읽습니다**(원시 데이터를 직접 읽음).
- 실시간 집계와 재계산이 **같은 서비스 인스턴스를 같이 쓰면 서로 간섭**합니다. 그래서 재계산 전용 서비스를 따로 둡니다.
- 즉 "실시간 처리 과정이 과거 데이터 재처리와 엉키는 일을 막기 위해서"입니다.

## 4-3. 시간 (이벤트 시각 vs 처리 시각)

### 두 가지 시각

| 시각 | 뜻 | 예 |
|---|---|---|
| 이벤트 시각 (event time) | 광고 클릭이 실제로 발생한 시각 | 사용자가 10:00:05에 클릭 |
| 처리 시각 (processing time) | 집계 서버가 그 클릭을 처리한 시각 | 집계 서버가 10:00:50에 처리 |

- 네트워크 지연이나 비동기 처리(데이터가 메시지 큐를 거쳐야 함) 때문에 두 시각의 차이는 커질 수 있습니다.
- 책의 예(그림 6.12): **이벤트 1이 집계 서비스에 무려 다섯 시간 뒤에 도착했습니다.**

### 어느 시각을 쓸까 (책 표 6.18)

| 방식 | 장점 | 단점 |
|---|---|---|
| 이벤트 발생 시각 | 클릭이 일어난 시점을 클라이언트가 정확히 아므로 집계 결과가 더 정확 | 클라이언트가 만든 시간에 의존하므로, 클라이언트 시계가 틀렸거나 악의적 사용자가 시간을 고칠 수 있음 |
| 처리 시각 | 서버 시간이므로 클라이언트보다 안정적 | 이벤트가 시스템에 도착한 시각이 한참 뒤인 경우 집계 결과가 부정확해짐 |

**책의 선택: 이벤트 발생 시각을 쓴다.** 정확도가 매우 중요하기 때문입니다. 다만 이때 "늦게 도착한 이벤트"를 어떻게 처리할지가 다음 과제입니다.

## 4-4. 워터마크와 늦게 온 이벤트

### 문제 상황 (책 그림 6.13, 1분짜리 텀블링 윈도우)

- 이벤트 2가 처리 시점에 너무 늦게 와서 **윈도우 1에 들어가지 못합니다.** (윈도우 1은 이미 닫히고 나서 버려짐)
- 이벤트 5도 **윈도우 3에 맞지 않습니다.**

### 해결: 워터마크 (책 그림 6.14)

- 각 윈도우 마지막에 **여분의 사각형**을 붙입니다. 그 사각형이 워터마크입니다.
- 워터마크는 집계 윈도우를 **조금 늘리는 것**으로 봅니다.
- 예: 15초 워터마크를 윈도우마다 붙이면
  - 윈도우 1이 이벤트 2를 집계할 수 있습니다.
  - 윈도우 3이 이벤트 5를 집계할 수 있습니다.
- 이렇게 하면 집계 결과의 정확도가 올라갑니다.

### 워터마크의 크기는 어떻게 정하나

| 워터마크 길이 | 좋은 점 | 나쁜 점 |
|---|---|---|
| 길다 | 늦게 도착하는 이벤트도 포착 가능 → 정확도 상승 | 기다리는 시간이 늘어 전체 지연이 커짐 |
| 짧다 | 응답이 빠름 | 늦은 이벤트 일부를 놓침 → 정확도 감소 |

- 워터마크 기법으로도 **너무 늦게 도착한 이벤트는 끝내 처리할 수 없습니다.** 그런 이벤트를 위해 시스템을 복잡하게 만들면 투자 대비 효능(ROI)이 떨어집니다.
- 사소한 데이터 오류는 **하루치 데이터 처리를 마감할 때 조정**할 수 있습니다(조정 절 참고).
- 정리: 워터마크를 쓰면 데이터 정확도는 높아지지만 **대기 시간이 늘어나서** 전반적인 지연 시간은 늘어납니다.

## 4-5. 집계 윈도우 (텀블링과 슬라이딩)

마틴 클레프만(Martin Kleppmann)의 책 《데이터 중심 애플리케이션 설계》에 따르면 윈도우에는 **네 종류**가 있습니다. 텀블링(고정), 호핑(hopping), 슬라이딩(sliding), 세션(session). 이 중 이 설계와 관련 있는 **텀블링**과 **슬라이딩**만 봅니다.

### 텀블링 윈도우 (책 그림 6.15) → 요구사항 1에 사용

- 시간을 같은 크기의 **겹치지 않는 구간**으로 나눕니다.
- 그래서 **매 분 발생한 클릭을 집계하기에 아주 적합**합니다.

```
분:      1         2         3         4         5
         |---------|---------|---------|---------|
         클릭 수    클릭 수    클릭 수    클릭 수
```

### 슬라이딩 윈도우 (책 그림 6.16) → 요구사항 2에 사용

- 데이터 스트림을 **미끄러져(sliding) 나아가면서**, 같은 시간 구간 안에 있는 이벤트를 집계합니다.
- 슬라이딩 윈도우는 **서로 겹칠 수 있습니다.**
- 그래서 "지난 M분 동안 가장 많이 클릭된 상위 N개 광고"를 알아내기에 적합합니다.

```
분:        1       2       3       4       5
         [--- 지난 3분 ---]
                 [--- 지난 3분 ---]        (1분씩 미끄러짐)
```

### 정리

| 요구사항 | 맞는 윈도우 |
|---|---|
| 매 분 클릭 수 집계 (요구 1) | 텀블링 |
| 지난 M분 상위 N개 광고 (요구 2) | 슬라이딩 |

## 4-6. 전달 보장 (메시지가 몇 번 전달되나)

### 왜 중요한가

- 집계 결과는 **과금**에 쓰이므로 데이터의 정확성과 무결성이 아주 중요합니다.
- 시스템은 다음 두 질문에 답할 수 있어야 합니다.
  - 이벤트의 **중복 처리**를 어떻게 피할 수 있는가?
  - **모든 이벤트의 처리**를 어떻게 보장할 수 있는가?

### 카프카 같은 메시지 큐의 세 가지 전달 방식

| 방식 | 뜻 | 특징 |
|---|---|---|
| 최대 한 번 (at-most once) | 한 번만 보내고, 실패해도 다시 보내지 않음 | 유실 가능, 중복 없음 |
| 최소 한 번 (at-least once) | 응답을 못 받으면 다시 보냄 | 유실 없음, **중복 가능** |
| 정확히 한 번 (exactly once) | 유실도 중복도 없게 | 가장 어렵고 비쌈 |

### 어떤 방식을 택할까

- 약간의 중복이 괜찮다면 대체로 **최소 한 번**이 적절합니다.
- 하지만 이 설계가 다루는 시스템은 그렇지 않습니다. **데이터의 몇 퍼센트 차이가 수백만 달러 차이로 이어질 수 있습니다.**
- 그래서 책은 **정확히 한 번** 방식을 권장합니다.
- 실제 광고 집계 시스템이 어떻게 구현했는지 더 알고 싶다면 엘프(Yelp)가 이를 어떻게 구현했는지 살펴보라고 권합니다 [17].

## 4-7. 데이터 중복 제거 (중복이 생기는 두 가지 경우)

가장 흔한 데이터 품질 문제가 중복입니다. 중복은 두 경우에 생깁니다.

### 경우 1: 클라이언트 쪽에서 같은 이벤트를 여러 번 보냄

- 예: 한 클라이언트가 같은 클릭을 여러 번 전송합니다. 악의적인 의도로 보내는 경우도 있습니다.
- 대응: **광고 사기/위험 제어(ad fraud/risk control)** 컴포넌트가 맞습니다. 더 알고 싶다면 [18]을 보세요.

### 경우 2: 집계 서비스 노드에 장애가 발생함 (책 그림 6.17)

이 순서대로 동작합니다.

1. 집계 서비스가 업스트림 카프카에서 이벤트를 가져옴 (폴)
2. 오프셋 100부터 소비
3. 100~110 이벤트 집계
4. 집계 결과를 다운스트림에 전송
5. 다운스트림이 수신 응답(ack)을 보냄
6. 업스트림에 "110까지 소비했음"을 응답

**문제:** 4번은 보냈는데 6번 전에 장애가 나면, 복구 후 **오프셋 100부터 다시 소비**해야 합니다. 그러면 100~110 이벤트는 이미 다운스트림에 가 있어서 **중복**이 됩니다.

> 오프셋(offset): 카프카에서 "어디까지 읽었는지"를 적은 번호입니다.

### 해결 시도 1: 오프셋을 외부 저장소에 기록 (책 그림 6.18)

- 오프셋을 HDFS나 S3 같은 외부 파일 저장소에 저장하면, 복구할 때 마지막 오프셋부터 이어서 처리할 수 있습니다.
- **문제:** 집계 결과를 다운스트림으로 보내기 **직전에** 오프셋을 먼저 저장합니다. 그 사이에 장애가 나면, 오프셋은 110인데 집계 결과는 전송되지 않은 상태가 됩니다. 복구 후 110 이전 이벤트는 무시되므로 **이벤트 유실**이 생깁니다.

### 해결 시도 2: 수신 확인을 받은 뒤에 오프셋 저장 (책 그림 6.19)

- 순서를 바꿔서, **다운스트림의 수신 확인 응답을 받은 뒤에 오프셋을 저장**합니다.
- 이렇게 하면 오프셋을 저장하기 전에 장애가 나도, 복구 후 100~110 이벤트를 다시 보낼 수 있습니다.
- 즉 유실이 생기지 않습니다. 대신 중복 가능성이 남습니다.

### 해결 시도 3: 분산 트랜잭션 (책 그림 6.20)

- **정확히 한 번** 처리하려면 **4단계부터 6단계까지를 하나의 분산 트랜잭션에 넣어야** 합니다.
- 분산 트랜잭션: 여러 노드에서 동작하는 트랜잭션입니다. 그 안에서 작업 가운데 **하나라도 실패하면 모든 작업의 상태를 실행 전으로 되돌립니다.**
- 대규모 시스템에서 중복을 없애기는 매우 어렵습니다. 이벤트를 정확히 한 번 처리하는 것은 난이도가 아주 높은 작업입니다.
- 자세한 내용이 궁금하면 [9]를 읽어 보세요.

# 5. 시스템 규모 확장

## 5-1. 성장 가정

- 사업은 매년 **30%씩 성장**합니다. 그러면 **트래픽은 3년마다 두 배**가 됩니다.
- 이 성장세를 뒷받침하려면 어떻게 해야 할까요?
- 이 설계안은 **메시지 큐, 집계 서버, 데이터베이스**의 세 가지 독립 구성 요소로 이루어져 있습니다. 서로 결합도가 낮으므로 각각 독립적으로 규모를 늘릴 수 있습니다.

## 5-2. 메시지 큐의 규모 확장

- **생산자(producer)**: 생산자 인스턴스 수에는 제한을 두지 않으므로, 확장이 쉽습니다.
- **소비자(consumer)**: 소비자 그룹 안에서 **재조정(rebalancing)** 메커니즘이 노드를 추가하거나 삭제할 수 있게 합니다. 그림 6.21은 소비자 2개를 4개로 늘린 예입니다.
  - 주의: 소비자가 수백 개면 재조정에 수 분 이상 걸릴 수 있습니다. 그래서 **시스템 사용량이 적은 시간에** 하는 것이 좋습니다.

### 브로커(broker) 설계

- **해시 키**: 같은 `ad_id`를 가진 이벤트는 **같은 카프카 파티션**에 저장해야 합니다. 그래서 `ad_id`를 해시 키로 씁니다. 그러면 집계 서비스는 같은 `ad_id`의 이벤트를 한 파티션에서 전부 읽을 수 있습니다.
- **파티션 수**: 파티션 수가 바뀌면 같은 `ad_id`의 이벤트가 **다른 파티션에 기록**되는 일이 생길 수 있습니다. 그러므로 미리 충분한 파티션을 확보하고, 운영 중에 파티션을 동적으로 늘리는 일은 피하는 것이 좋습니다.
- **토픽의 물리적 샤딩**: 하나의 토픽만으로 충분한 경우는 거의 없습니다. 지역별 토픽(`topic_north_america`, `topic_europe_topic_asia` 등)이나 유형별 토픽(`topic_web_ads`, `topic_mobile_ads` 등)으로 나눌 수 있습니다.
  - 장점: 처리 대역폭이 넓어지고, 소비자 그룹 재조정 시간이 줄어듭니다.
  - 단점: 복잡성이 늘고 유지 관리 비용이 늘어납니다.

## 5-3. 집계 서비스의 규모 확장

- 집계 서비스는 본질적으로 **맵리듀스 연산**으로 구현됩니다.
- 그림 6.22: 카프카 → 집계 서버 1~3 (각 서버 안에 분배 프로세스와 축약 프로세스) → 최종 결과. 노드를 더하거나 빼서 **수평으로** 조정합니다.

**처리 대역폭을 높이는 두 가지 방법**

| 방안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| #1 다중 스레드 (그림 6.23) | ad_id마다 별도 처리 스레드를 두는 방식. 예: 노드 A는 ad_id 1~3, 노드 B는 ad_id 4~6 | 구현이 쉽고, 자원 공급자에 대한 의존이 없음 | 노드 한 대의 양에 한계가 있음 |
| #2 자원 공급자에 배포 (YARN 등) | 집계 서비스 노드를 자원 공급자에 배포해 다중 프로세싱 활용 | 컴퓨팅 자원을 추가해 규모 확장 가능. 실제로는 이 방식이 더 많이 쓰임 | 구현이 더 복잡함, 자원 공급자에 의존 |

> 책은 실제 사용은 두 번째(#2)가 더 많다고 합니다.

## 5-4. 데이터베이스의 규모 확장 (카산드라)

- 카산드라는 **안정 해시(consistent hash)**와 비슷한 방식으로 수평 확장을 지원합니다.
- 데이터는 각 노드에 고루 분산됩니다. 각 노드는 **해시 링** 위의 특정 구간을 담당하고, 다른 가상 노드의 데이터 사본도 보관합니다.
- 그림 6.24 **가상 노드**: 노드를 추가하면 가상 노드 간의 균형이 **자동으로 다시 조정**됩니다. 샤딩을 수동으로 조정할 필요가 없습니다.

## 5-5. 핫스팟 문제

- **핫스팟(hotspot)**: 다른 서비스나 샤드보다 더 많은 데이터를 받는 서비스나 샤드입니다.
- 광고 클릭 집계에서는 큰 회사가 수백만 달러 예산을 집행하고, 그런 회사의 광고에는 클릭이 많이 발생합니다.
- 이벤트 파티션을 `ad_id`로 나누기 때문에, 어떤 집계 노드는 다른 노드보다 훨씬 많은 클릭을 받게 됩니다. 그러면 **서버 과부하**가 생깁니다.

**해결: 집계 노드를 더 할당** (책 그림 6.25, 각 노드가 100개 이벤트만 처리한다고 가정)

1. 집계 노드에 300개 이벤트가 도착 → 한 노드가 감당할 수 있는 양을 초과 → **자원 관리자**에게 추가 자원 요청
2. 자원 관리자가 집계 노드 2개를 추가로 할당
3. 원래 노드가 100개씩 처리하도록 이벤트를 **3개 그룹으로 나눠** 분배
4. 집계가 끝나면 축약 결과를 원래 집계 노드에 기록

- 더 복잡한 방법도 있습니다: **전역-지역 집계(Global-Local Aggregation)**, **분할 고유 집계(Split Distinct Aggregation)**. 자세한 내용은 [22]를 참고하세요.

# 6. 결함 내성 (장애가 나도 버티기)

## 6-1. 문제

- 집계는 **메모리에서** 이루어집니다. 집계 노드에 장애가 생기면 집계 결과도 손실됩니다.
- 다만 업스트림 카프카 브로커에서 이벤트를 다시 받아오면 그 숫자를 다시 만들어 낼 수 있습니다.
- 카프카 데이터를 처음부터 다시 재생해서 집계하면 시간이 오래 걸립니다. 그래서 **시스템 상태를 스냅숏으로 저장**하고, 마지막으로 저장된 상태부터 복구해 나가는 것이 바람직합니다.
- 이 설계에서 "시스템 상태"에 해당하는 정보는 **업스트림 오프셋뿐만이 아닙니다.** 지난 M분 동안 가장 많이 클릭된 광고 N개 같은 데이터도 시스템 상태의 일부로 저장해야 합니다.

## 6-2. 스냅숏 예시 (책 그림 6.26)

지난 5분간 가장 많이 클릭된 광고 3개의 스냅숏입니다.

| 광고 | 1분 | 2분 | 3분 | 4분 | 5분 |
|---|---|---|---|---|---|
| ad1 | 1 | 3 | 2 | 3 | 3 |
| ad3 | 1 | 1 | 3 | 0 | 0 |
| ad2 | 0 | 2 | 0 | 1 | 0 |

## 6-3. 복구 절차 (그림 6.27)

1. 장애 난 노드를 **새 노드로 대체**합니다.
2. 새 노드는 **마지막 스냅숏**에서 데이터를 복구합니다.
3. 스냅숏 이후에 도착한 새 이벤트는 **새 노드가 카프카 브로커에서 다시 읽어서** 처리합니다.
- 그림 6.27: 외부 노드가 새 집계 노드를 만들고, 진행 중인 스냅숏(점진적 스냅)을 스냅숏 저장소에서 복구합니다.

# 7. 데이터 모니터링과 정확성

## 7-1. 왜 중요한가

- 집계 결과는 **RTB**와 **청구서 발행**에 쓰일 수 있습니다. 그러므로 시스템이 정상적으로 동작하는지 모니터링하고, 데이터 정확성을 보장하는 것은 아주 중요한 과제입니다.

## 7-2. 지속적으로 모니터링할 지표

| 지표 | 뜻 | 왜 보나 |
|---|---|---|
| 지연 시간 (latency) | 데이터를 처리하는 각 단계마다 지연 시간이 추가될 수 있음. 시스템의 중요 부분마다 시각(timestamp)을 추적하고, 기록된 시각 사이의 차이를 지연 시간 지표로 변환 | 어디서 늦어지는지 찾기 위해 |
| 메시지 큐 크기 | 큐의 크기가 갑자기 늘어나면 더 많은 집계 서비스 노드를 추가해야 할 수 있음 | 처리가 못 따라가고 있다는 신호 |
| 카프카 레코드 지연 (records-lag) | 카프카는 분산 커밋 로그 형태의 메시지 큐이므로, 카프카를 쓰는 경우 레코드 처리 지연 지표를 대신 추적 | 뒤처진 양을 봄 |
| 집계 노드의 시스템 자원 | CPU, 디스크, JVM 같은 것에 관계된 지표 | 노드 자체가 버거운지 |

## 7-3. 조정 (reconciliation)

- **조정**은 다양한 데이터를 비교해서 데이터 무결성을 보증하는 기법을 말합니다.
- 은행 업계라면 은행에서 만든 데이터와 비교하면 되겠지만, **광고 클릭 집계 결과는 비교할 제3자가 없습니다.**
- 한 가지 방법: 매일 각 파티션에 기록된 클릭 이벤트를 **일괄 처리**해서, 이벤트 발생 시각 기준으로 정렬된 결과를 만들고, 그것을 **실시간 집계 결과와 비교**합니다.
- 더 높은 정확도가 필요하면 더 작은 윈도우(예: 1시간)를 사용합니다.
- 주의: 일괄 결과와 실시간 결과가 **정확히 일치하지 않을 수 있습니다.** 늦게 도착한 이벤트 때문입니다(4-4 워터마크 절 참고).

## 7-4. 최종 설계안 (책 그림 6.28)

```
[로그 모니터] -> [메시지 큐] -> [데이터 집계 서비스] -> [메시지 큐] -> [DB 기록] -> [집계 결과 DB] <- [질의 서비스(대시보드)]
      |                                                                   ^
      v                                                                   |
[DB 기록] -> [원시 데이터 DB] <- [재계산 서비스] -> [재계산 전용 집계] -> [메시지 큐]
                                 ^
                                 |
                              [조정] -> (집계 결과 DB에 반영)
```

(위 그림은 핵심 연결만 단순화한 것입니다. 책의 그림 6.28을 보면 정확한 화살표 방향을 확인할 수 있습니다.)

# 8. 대안적 설계안 (일래스틱서치 없이)

- 일반적인 시스템 설계 면접에서는 빅데이터 파이프라인 전문 소프트웨어의 동작 메커니즘까지는 묻지 않습니다.
- 대신 **사고 과정**과 **타협적 선택지의 장단점을 설명하는 능력**을 봅니다.
- 다른 한 가지 가능한 설계안: 광고 클릭 데이터를 **하이브(Hive)**에 저장하고, 일래스틱서치 계층을 없애서 처리합니다. 집계는 **클릭하우스(ClickHouse)** 또는 **드루이드(Druid)** 같은 OLAP 데이터베이스로 처리합니다. (그림 6.29)
  - 그림 6.29 흐름: 로그 모니터 → 메시지 큐 → 위험성 통제 엔진(Risk Control Engine) → 하이브 / 클릭하우스 → (고객 대상 애널리틱스, 데이터 과학자가 질의)
- 이 설계안에 대한 더 자세한 내용은 [25]를 참고하세요. (우버 사례: 아파치 플링크 + 카프카 + 피노)
