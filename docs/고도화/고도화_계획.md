## 1. 슬라이딩 윈도우 중복 질문에 대한 답

- 윈도우가 겹치는 것은 **계산 과정**입니다. 같은 클릭이 여러 윈도우 계산에 들어가는 것은 정상입니다.
- 중복이 생기는 경우는 **윈도우 결과를 더해서 저장할 때**입니다. 1분마다 밀리는 5분 윈도우에서 클릭 1건은 5개 윈도우에 들어갑니다.
- 해결: **저장은 겹치지 않는 분 버킷만 하고**, 윈도우 값은 버킷을 합해서 조회 시 계산합니다.
- 상위 N 결과는 분마다 **덮어쓰고** 더하지 않습니다.
- 재전송으로 같은 클릭이 두 번 오는 중복은 슬라이딩과 무관하며, `notification_id` 로 막습니다.

### 3-2. DB: 실제 SQL 확인, N+1·인덱스·쿼리 튜닝

**(a) 실제 나가는 SQL 확인**
- `spring.jpa.show-sql` 또는 `pg_stat_statements` 로 요청 한 번에 나가는 SQL 개수를 센다.
- 배너 요청 한 번에 최소 SQL: 대상 유저 조회 1 + 캠페인 선택 1 + 노출 INSERT 1 + 집계 UPSERT 1 = **4개**. 이 숫자를 기록한다.

**(b) `findRandomActiveForTarget` 튜닝**
- 문제: `ORDER BY random()` 은 조건에 맞는 행을 **전부 읽고 정렬**한다. 광고가 늘수록 느려진다.
- 변경 1 (인덱스): 조건 컬럼에 부분 인덱스
  ```sql
  CREATE INDEX idx_campaigns_active_age
    ON campaigns (time_start, time_end)
    WHERE status = 'ACTIVE' AND deleted_at IS NULL;
  ```
- 변경 2 (선택 방식): `random()` 대신 3-4의 eCPM 정렬로 바꾼다 (4절 참고). 【정정 2026-10-29: eCPM·CTR 미사용, 입찰가 기준 확률 뽑기 (4절 확정)】 이때 질의는 "후보 목록 조회"와 "점수 계산"으로 나뉜다.
- 검증: `EXPLAIN (ANALYZE, BUFFERS)` 결과를 개선 전후로 기록.

**(c) N+1 확인**
- `CampaignStatsStreamService` 는 구독자마다 `campaign_stats` 를 읽는다. 구독자가 N명이면 같은 행을 N번 읽는다. 문서 3-3의 "캠페인별로 묶어 한 번만 읽기"로 해결한다.
- 대시보드 목록/상세에서 캠페인마다 통계를 따로 읽는 부분이 있는지 확인이 필요하다 (아직 확인 안 함).

**(d) 쓰기 쪽**
- 노출·클릭의 집계 UPSERT 는 3-3에서 분리한다. 여기서는 원본 INSERT 만 남긴다.

### 3-3. 구조: 캐시, 비동기 처리, 장애 대응

이 칸이 가장 큰 변경입니다. **단계로 나눠서 진행**합니다.

#### 분 버킷 도입 (추가 인프라 없음, 먼저 한다)

현재 `campaign_stats` 누적 한 행을 **분 버킷 표**로 바꿉니다.

```
campaign_minute_stats (campaign_id, minute_bucket, sent_count, click_count)
   PK = (campaign_id, minute_bucket)      -- minute_bucket 은 분 단위로 자른 시각
```

- 노출/클릭 요청은 여전히 같은 트랜잭션에서 이 표에 UPSERT 한다. 핫 로우는 **분이 바뀌면 다른 행**이 되므로 잠금이 나뉜다. (완전한 해결은 아니고 경감)
- "최근 M분" = `minute_bucket >= now - M분` 인 행의 합. 윈도우가 겹쳐도 버킷은 하나이므로 중복 없음 (1절).
- 기존 `campaign_stats` 는 호환을 위해 당분간 유지하고, 대시보드 읽기 경로만 바꾼다.
- **상위 N (지금)**: 같은 분 버킷을 합계로 읽어 M분 상위 N 을 구한다 (6-1 ③). 결과는 1분 캐시. Redis 없이 한다.

#### 최종 구조 (그림 기준, 확정)

```
[클릭 처리 서비스] (POST /clicks, 따로 실행)
   └ click_events + outbox_events (한 트랜잭션) → 응답 (집계 기다리지 않음)
        │ 릴레이 (outbox → Kafka)
        ▼
[Kafka click-events] (파티션 3, 키 = campaign_id)
   ├─ ClickHouse (Kafka 엔진, 앱 코드 없음)
   │     click_raw (ReplacingMergeTree, notification_id 로 중복 제거)
   │     └ 구체화 뷰 → click_facts (분·연령대·성별 합계)  ← 대시보드 추이·상위 N 이 읽음
   └─ 재집계 서비스 (Spring, 같은 프로그램에서 Kafka 읽기 + cron)
         ├ 원본을 AWS S3 raw-clicks/{y}/{m}/{d}/{h}/ 에 저장
         └ cron (매일 새벽): 전날 기간을 S3 원본에서 다시 계산 → click_facts 해당 날짜를 덮어씀

[집계 대시보드]  클릭 추이·상위 N ← ClickHouse  /  노출 수 ← PostgreSQL
```

**확정 결정**
1. **집계 위치**: ClickHouse (구체화 뷰). 앱에서 분 단위로 묶지 않는다. 그래서 **큐 2 없음**, **합치기 방식 없음** (상위 N 은 ClickHouse 가 합산·정렬).
2. **앱 소비자**: 재집계 서비스 1개 (Kafka 읽기 + cron 을 같은 프로그램에). ClickHouse 의 소비자는 Kafka 엔진 설정으로 파티션 수 안에서 늘린다.
3. **노출은 Kafka 로 보내지 않는다.** 노출 수는 PostgreSQL (`campaign_stats.sent_count`, 분 버킷의 노출 열) 에 계속 동기 UPSERT. 그래서 노출 전용 ClickHouse 표(`impression_facts`)는 만들지 않는다.
4. **중복 보정**: Kafka 는 같은 메시지를 두 번 줄 수 있다. ClickHouse 실시간 값은 **잠정**이고, 재집계 cron 이 S3 원본으로 덮어쓴 값이 **확정**이다. 원본 표 `click_raw` 는 `notification_id` 로 중복을 없앤다.
5. **PostgreSQL 클릭 열**: Kafka 연결과 함께 클릭 UPSERT 를 요청 경로에서 뺀다 (집계 잠금 제거가 목적). 대시보드 클릭은 ClickHouse 에서 읽는다. PostgreSQL 분 버킷의 클릭 열은 갱신이 멈추고, 열 삭제는 조정이 안정된 뒤에 정한다.
6. **조정**: 매일 PostgreSQL `click_events` 행 수 = ClickHouse `click_raw` (중복 제거) 행 수. 차이 0 이 기준이고 허용 오차는 없다. 불일치하면 로그 경고.
7. **파티션 3개로 시작**, 키는 `campaign_id`. 몰리면 파티션을 늘리거나 키에 해시를 붙여 분산한다 (측정 후, 5-2·5-5). 합산은 ClickHouse 가 하므로 분산해도 결과는 같다.
8. **실행 단위**: 클릭 처리 서비스와 재집계 서비스는 같은 코드베이스에서 **따로 실행**한다 (서버를 늘리는 것이 아님). 나머지 API 는 기존 실행 단위.
9. **상위 N·추이 질의**: 1단계는 PostgreSQL 분 버킷, Kafka 연결 뒤에는 ClickHouse `click_facts` 에서 같은 모양으로 읽는다. 윈도우 규칙 (3-6) 은 그대로.

#### ClickHouse·S3 (Kafka 연결 이후), Redis (그림대로, 캐시 용도)

결정된 구성입니다. 역할은 아래와 같습니다.

| 부품 | 맡는 일 | 대체 가능했던 것 |
|---|---|---|
| Kafka `click-events` | 클릭 이벤트 전달 (ClickHouse 와 재집계 서비스가 각각 읽음) | outbox 표 |
| ClickHouse `click_facts` | 분 단위 집계, 추이·상위 N·필터 질의 | PostgreSQL 분 버킷 |
| AWS S3 `raw-clicks/...` | 원본 보관, 재계산 입력 | 원본 DB 테이블 |
| Redis | 최근 M분 상위 N, 캠페인 후보 캐시 | 질의 시 계산 |

**Redis 상위 N 설계 (책의 `most_clicked_ads` 대응) — 참고용 설계**
> 지금은 PostgreSQL 합계로 한다 (6-1 ③). 아래는 측정에서 합계 질의가 느릴 때 바꿀 설계다.
```
키: ad:clicks:{yyyyMMddHHmm}   (분마다 1개, TTL 2시간)
값: 정렬 집합(Sorted Set)  member = campaign_id, score = 클릭 수
갱신: ZINCRBY ad:clicks:202610291200 1 {campaign_id}   (클릭 1건마다)
조회: ZUNIONSTORE tmp:top M개키 → ZREVRANGE tmp 0 N-1 WITHSCORES
      결과는 1분 동안 캐시하고, 키를 지운다
```
- 분 키는 겹치지 않으므로 M분 합계에 중복이 없다.
- 상위 N 조회마다 합치기를 하면 비싸므로 결과를 캐시한다 (3-3의 캐시).

**캐시**
- 연령대별 "지금 진행 중인 캠페인 후보 목록": Redis 또는 앱 메모리, TTL 30~60초.
- 캠페인 생성·수정·상태 변경 때 해당 캐시 무효화. 무효화 누락 시 최대 TTL 만큼 옛 목록이 나온다 (허용 여부는 정할 것).

**장애 대응 (책 6장 결함 내성)**

| 고장 난 것 | 영향 | 대응 |
|---|---|---|
| Kafka | 집계 지연. 원본 저장은 정상 | outbox 가 쌓였다가 복구 후 재전송 |
| Redis | 상위 N 조회 실패 | ClickHouse 최근 분 질의로 대체 (느리지만 정확) |
| ClickHouse | 추이 차트 실패 | PostgreSQL 분 버킷 최근 24시간으로 제한 대체 |
| 집계 워커 장애 | 집계 멈춤 | 마지막 처리 오프셋(또는 outbox 상태)부터 재개 |
| 같은 이벤트 중복 전송 | 과다 집계 | `notification_id` 기준 중복 제거 (발행 전 + 소비 쪽) |

**책의 스냅숏 개념 적용: 하지 않음 (확정, 2026-10-29).** `top_ads_snapshot` 은 만들지 않는다 (`ERD_데이터명세.md` 2-9). Redis 가 날아가면 상위 N 을 분 버킷(또는 ClickHouse)에서 다시 계산한다.

**SSE 방식**: 현재 2초 폴링. Kafka 연결 뒤에 바꿀지는 정할 것 (아래 8절). 최소한 "캠페인별 한 번 읽기"는 바로 한다.

### 3-4. 운영: 모니터링 설계 (우리 서비스 기준)

**도구**: Spring Actuator + Micrometer 로 앱이 지표를 노출 → Prometheus 가 주기적으로 가져감 → Grafana 로 그래프 (Prometheus·Grafana 는 P3).

**노출 설정**
- Actuator 로 여는 주소: `health`, `prometheus` 만. 나머지(`env`, `beans` 등)는 닫는다.
- **현재 상태 (2026-10-29 확인)**: develop `application.yml` 은 `include: health,info` 다. `prometheus` 는 아직 없다. 지표 노출을 하려면 Micrometer Prometheus 의존성과 설정 변경이 같이 필요하다 (O1 작업에 포함).
- `/actuator/prometheus` 는 내부 네트워크에서만 접근한다 (광고주 API 와 섞이지 않게).
- Prometheus 수집 주기: 15초.

**지표 설계**

| 지표 이름 (Micrometer) | 종류 | 어디서 재나 | 어떻게 재나 | 목적 |
|---|---|---|---|---|
| `click_requests_total{result}` | 카운터 | 클릭 처리 서비스 (`ClickService`) | 결과(`created`·`duplicate`·`not_found`)마다 +1 | 클릭이 정상 처리되는지, 중복이 얼마나 오는지 |
| `outbox_pending_count` | 게이지 | 클릭 처리 서비스 | 15초마다 `published_at IS NULL` 행 수 (부분 인덱스 사용) | 릴레이가 밀리는지 |
| `outbox_oldest_pending_age_seconds` | 게이지 | 클릭 처리 서비스 | 가장 오래된 미발행 행의 `created_at` 과 지금의 차이 | 릴레이가 멈췄는지 (가장 중요한 경고 신호) |
| `outbox_relay_published_total` / `outbox_relay_failures_total` | 카운터 | 릴레이 (`OutboxRelay`) | 발행 성공·실패마다 +1 | 릴레이가 일하는지, 실패가 있는지 |
| `click_processing_lag_seconds` | 게이지 (5분 평균·p95) | ClickHouse 조회 작업 | `ingested_at − clicked_at` 의 p95 를 5분마다 계산 | 클릭부터 집계 반영까지 걸리는 시간 |
| `kafka_consumer_lag` (ClickHouse 소비자) | 게이지 | ClickHouse `system.kafka_consumers` | 주기적으로 조회해서 게이지로 노출 | ClickHouse 가 밀리는지 |
| `kafka_consumer_lag` (재집계 서비스) | 게이지 | 재집계 서비스 | Spring Kafka 가 내는 lag 지표 그대로 | 재집계 쪽 소비가 밀리는지 |
| `recompute_runs_total{status}` | 카운터 | 재집계 cron 작업 | 성공·실패마다 +1 | 재계산이 매일 도는지 |
| `recompute_last_success_timestamp` | 게이지 | 재집계 cron 작업 | 성공 시각을 기록 | 몇 시간 동안 성공이 없는지 |
| `recompute_unique_clicks` | 게이지 | 재집계 cron 작업 | 마지막 실행의 고유 클릭 수 | 재계산 결과의 규모 확인 |
| `reconcile_diff{pair}` | 게이지 | 조정 작업 | 세 쌍(PG↔S3, S3↔ClickHouse)의 차이 | 0 이어야 함 |
| `s3_write_failures_total` | 카운터 | 재집계 서비스의 S3 저장 | 실패마다 +1 | 원본이 빠질 위험 |
| `stats_cache_requests_total{result}` | 카운터 | `StatsQueryService` | Redis `hit`·`miss`·`error` | 캐시가 동작하는지 |
| `stats_fallback_active` | 게이지 | `StatsQueryService` | ClickHouse 대신 PostgreSQL 을 쓰면 1 | 자동 전환이 걸렸는지 |
| `http_server_requests_seconds` | 타이머 (자동) | Actuator 기본 | 통계 API 경로별 응답 시간 | 광고주 화면이 느린지 |
| `hikaricp_connections_pending` | 게이지 (자동) | Actuator 기본 | DB 연결을 기다리는 요청 수 | 행 잠금·연결 부족 |
| `jvm_memory_used_bytes`, `process_cpu_usage` | 게이지 (자동) | Actuator 기본 | 메모리·CPU | 자원 한계 |

**열 추가 (지연 측정용)**: `click_raw` 에 `ingested_at DateTime DEFAULT now()` 를 넣는다. 구체화 뷰가 채우므로 ClickHouse 가 언제 받았는지 남는다. `click_processing_lag_seconds` 는 이 값에서 계산한다.

**경고 기준 (초안)**

| 경고 | 조건 | 의미 |
|---|---|---|
| 릴레이 멈춤 | `outbox_oldest_pending_age_seconds > 300` | 5분째 발행이 안 됨 |
| 실시간 지연 | `click_processing_lag_seconds` p95 > 60 | 대시보드가 1분 넘게 늦음 |
| Kafka 밀림 | lag 이 5분 동안 계속 증가 | 소비자가 못 따라감 |
| 재계산 실패 | `recompute_runs_total{status="failed"}` 증가 | 즉시 확인 |
| 재계산 누락 | `recompute_last_success_timestamp` 가 26시간 넘게 옛날 | 하루 실행이 빠짐 |
| 조정 차이 | `reconcile_diff` ≠ 0 | 데이터가 빠졌거나 틀림 |
| S3 저장 실패 | `s3_write_failures_total` 증가 | 원본 유실 위험 |
| 연결 대기 | `hikaricp_connections_pending > 0` 1분 이상 | DB 병목 |
| 자동 전환 중 | `stats_fallback_active == 1` 10분 이상 | ClickHouse 가 오래 죽어 있음 |

**대시보드 패널 (Grafana, P3)**: 릴레이 대기 시간, 실시간 지연 p95, Kafka lag, 재계산 최근 성공 시각, 조정 차이, 통계 API 응답 시간, DB 연결 대기.

**결정 / 보류 / 미정**
- 결정: 위 지표 이름과 위치, Actuator 는 `health`·`prometheus` 만 연다.
- 보류: Grafana 대시보드 (P3).
- 미정: 경고 기준 수치 (측정 후 조정), 경고 채널.

**권한·보안 체크 (새 API 공통)**
- 새 `GET` 2개 모두 `@AdvertiserId` 를 붙인다. 빠지면 공개 API가 되므로 리뷰 때 확인한다 (CLAUDE.md 인증 규칙).

**운영 설정 (API 아님, 같이 해야 함)**

**문서 반영 (코드 밖)**
- Notion API 명세서에 A1, A2, M3~M6 추가 (사용자가 직접, 요청 시 수정).

**정할 것 (사용자)**
1. A2 상위 N 범위: 내 캠페인 중 상위 N 으로 할지 (추천), 전체 중 상위 N 도 같이 할지.

3. M6 기본 배너 응답 형식: `isDefault` 필드로 할지, 별도 응답으로 할지.
4. M8: 진행 중 캠페인의 예산·입찰가를 막을지 (추천: 막음).

**상위 N 윈도우 규칙 (3-5 A2, 6-1 ③·⑧, 6-3 과 맞춤)**
- 입력 `windowMinutes`: 기본 1, 최대 60. **1분의 배수만 가능** (분 버킷이 1분 단위라서 30초 윈도우는 만들 수 없다).
- 윈도우는 **저장하지 않는다**. 조회할 때 `from = 지금 - windowMinutes분` 으로 계산해서 분 버킷 행을 합한다. 그래서 윈도우 크기마다 표를 따로 두지 않는다.
- 윈도우 크기를 열로 저장하는 곳은 없다 (`top_ads_snapshot` 은 만들지 않는다, 확정).
- 캐시 키: `(범위, windowMinutes, ageGroup, gender, limit, 분 단위 시각)`. 윈도우 크기를 키에 넣어서 1분 결과를 5분 질의에 재사용하지 않는다. 캐시 TTL 1분.
- `limit` 최대 100.
- **왜 슬라이딩 윈도우를 저장하지 않나 (되돌리지 말 것)**
  - 클릭 1건이 M개 윈도우에 들어가므로, 미리 저장하면 행이 M배가 되고 클릭마다 M줄을 고쳐야 한다.
  - 윈도우끼리 겹치므로 그 값을 다시 더하면 같은 클릭이 중복으로 세어진다.
  - 저장은 겹치지 않는 1분 칸 하나로 두고, 조회 때 칸을 더하면 중복 없이 어떤 윈도우든 계산된다 (책 4-5).
- ClickHouse 로 옮긴 뒤에도 `windowMinutes` 는 쿼리의 기간 인자로 남는다 (Redis 키 `ad:top:{window}:...` 도 같은 규칙).

| 2 조회 API·SSE | A1, A2, M1 | 민서 | `stats` 도메인 |
| 3 예산·입찰 데이터 | M3~M5, M8, 표 3개 | 규보 | 캠페인 CRUD 담당 |
| 4 배너 매칭 | M6, M7 | 규보 | 배너 담당 (민서의 기록 서비스만 호출) |
| 6 Kafka 연결 | 릴레이, 재집계 서비스, 설정 | 민서 | 재집계 서비스가 S3 저장과 cron 을 함께 맡음 |
| 7 합치기 | 폐기 (ClickHouse 가 처리) | — | — |
| 8 ClickHouse·S3 | DDL, 읽기 전환, 재계산, 조정 | 민서 또는 협의 | 데이터 흐름 전체 |
| 프론트 연동 | `isDefault`, 새 API 화면 | 유민님 | API 명세 변경 후 |

**같이 묶는 이유**
- 1번과 6번은 같은 표를 씁니다. 한 사람이 맡아야 표 구조가 바뀔 때 충돌이 없습니다.
- `ClickService` 는 1번(분 버킷 호출)과 4번(배너·클릭 흐름)이 모두 건드립니다. 민서가 1번을 먼저 머지하고, 규보가 4번을 그 위에 얹는 순서가 안전합니다.
- `ErrorCode` 는 3번과 4번이 모두 추가합니다. 3번에서 한 번에 넣고 4번이 그 위에 쌓습니다.

**결정할 것**
1. 규보님과 위 담당 나눔이 맞는지 (3·4번을 규보님이 맡을지)
2. 0번 기준선 측정을 누가 할지
3. 5번 측정을 1~4번 끝날 때마다 할지, 한 번만 할지
4. 8번 ClickHouse·S3를 이번 일정에 넣을지

### 3-8. 재계산 방법 (A안 확정: ClickHouse 가 계산, 스프링은 실행만)

**한 줄 요약**: 재집계 서비스(스프링)가 매일 새벽 "어제·그저께"를 다시 계산하라고 ClickHouse 에 SQL 을 보낸다. ClickHouse 가 S3 원본을 읽어 `click_facts` 의 그 날짜 파티션을 통째로 바꿔 끼운다.

**흐름**
```
[재집계 서비스 (스프링)] cron 새벽 3시, 또는 수동 실행 (시작일·종료일)
   │ JDBC 로 ClickHouse 에 SQL 전송
   ▼
[ClickHouse]
   1) click_facts_stage 비우기
   2) s3() 로 S3 원본 읽기 → notification_id 로 중복 제거 → 분·연령대·성별 집계 → stage 에 쓰기
   3) REPLACE PARTITION: click_facts 의 해당 날짜 파티션을 stage 것으로 교체 (한 번에 바뀜)
   │ 결과 행 수를 스프링에 돌려줌
   ▼
[재집계 서비스] 조정 쿼리 실행 → recompute_log 에 기록 → 차이가 있으면 경고
```

**단계별 할 일**
1. **S3 저장 (Kafka 소비)**: 메시지를 받아 `raw-clicks/{yyyy}/{MM}/{dd}/{HH}/{배치ID}.json` 에 JSON Lines 로 쓴다. 날짜 폴더는 **클릭 시각(`clicked_at`)** 기준이다. 배치는 1분 또는 1,000건마다 파일을 닫는다.
2. **메시지 형식 고정 (snake_case 확정)**: `notification_id`, `campaign_id`, `age_group`, `gender`, `clicked_at` (서버가 받은 시각). Kafka 와 S3 가 같은 형식을 쓴다. 자세한 형식은 `ERD_데이터명세.md` 6절.
3. **재계산 SQL (ClickHouse)**
   ```sql
   INSERT INTO click_facts_stage
   SELECT campaign_id, toStartOfMinute(clicked_at) AS minute, age_group, gender, count() AS click_count
   FROM (
       SELECT notification_id,
              any(campaign_id) AS campaign_id,
              any(age_group)   AS age_group,
              any(gender)      AS gender,
              any(clicked_at)  AS clicked_at
       FROM s3('https://<bucket>.s3.ap-northeast-2.amazonaws.com/raw-clicks/2026/11/01/*/*.json',
               <access_key>, <secret_key>, 'JSONEachRow',
               'notification_id String, campaign_id Int64, age_group String, gender String, clicked_at DateTime')
       GROUP BY notification_id          -- 같은 클릭은 한 번만 센다
   )
   GROUP BY campaign_id, minute, age_group, gender;
   ```
   - S3 원본에도 Kafka 재전송으로 같은 클릭이 두 번 들어갈 수 있다. 그래서 `GROUP BY notification_id` 로 먼저 줄인다.
   - 날짜가 두 개면 경로를 두 번 쓰거나 와일드카드로 넓힌다.
4. **파티션 교체**
   ```sql
   ALTER TABLE click_facts REPLACE PARTITION 20261101 FROM click_facts_stage;
   ```
   - `click_facts` 는 `PARTITION BY toYYYYMMDD(minute)` 이어야 한다 (고도화 6-2 에 반영).
5. **조정 (스프링이 실행 후 확인)**: 같은 날짜에 대해 세 값을 비교한다.
   - PostgreSQL `click_events` 행 수
   - S3 원본의 고유 `notification_id` 수
   - ClickHouse `click_raw` 행 수 (중복 제거됨)
   세 값이 같아야 한다. 다르면 경고 로그를 남긴다.
6. **실행 기록**: 새 표 `recompute_log` (PostgreSQL) 에 대상 날짜, 시작·끝 시각, 읽은 파일 수, 고유 클릭 수, 교체 후 합계, 조정 결과를 남긴다.
7. **수동 실행**: 스프링에서 `recompute --from=2026-11-01 --to=2026-11-03` 같은 명령으로 실행한다. 관리자 API 로 만들 경우 인증을 붙인다 (CLAUDE.md 규칙).

**시각 기준 (확정: 처리 시각)**
- `clicked_at` = 서버가 클릭 요청을 받은 시각. Kafka 를 거쳐도 바꾸지 않는다 (메시지에 그대로 싣는다).
- 이벤트 시각(클라이언트가 보낸 시각)은 쓰지 않는다. 이유: 조작 위험, API·프론트 변경, 차이는 네트워크 지연 (수 초) 뿐.
- 책은 이벤트 시각을 권하지만, 우리는 온라인 클릭이고 규모가 작아서 효과가 작다. 오프라인 클릭 기능을 넣으면 다시 검토한다.

**이 방식이 안전한 이유**
- `REPLACE PARTITION` 은 한 번에 교체하므로, 재계산 중에 대시보드가 빈 값을 보지 않는다 (4-2 의 "빈 구간" 문제 해결).
- 같은 날짜를 여러 번 돌려도 결과가 같다 (멱등).
- 집계 규칙이 구체화 뷰와 같은 SQL 식이므로 로직이 한 벌이다 (람다 원칙, 4-1).

**주의**
- 재계산이 끝난 뒤 도착한 실시간 값은 다음 재계산 때 확정된다. 그래서 가장 최근 날짜는 잠정 값이다.
- S3 접근은 EC2 의 IAM 역할을 먼저 쓰고, 안 되면 환경변수 키를 쓴다. `.env.example` 에는 이름만 적는다.
- ClickHouse 가 S3 를 읽는지는 구현 전에 Testcontainers (MinIO, S3 호환) 로 먼저 확인한다.

**테스트 (구현 시)**
- 같은 클릭이 S3 에 두 번 있어도 한 번만 집계된다.
- 다음날 도착한 늦은 클릭이 재계산 후 전날 값에 들어간다.
- 같은 날짜를 두 번 실행해도 값이 같다.
- 재계산 전후 조정 차이가 0 이다.

**정할 것**
- 재계산 시각 (추천: 새벽 3시)
- 수동 실행 방식 (명령줄 또는 관리자 API)

### 3-10. 복구 코드 작업 (책 6장 결함 내성 기준)

**원칙**: 우리는 메모리 상태가 없으므로 스냅숏이 필요 없다. 대신 **구성 요소마다 죽었을 때 멈추는 것과 살아났을 때 따라잡는 방법**을 코드로 만든다.

| 장애 | 자동으로 할 일 (코드) | 테스트 | 사람이 할 일 |
|---|---|---|---|
| 릴레이 멈춤 | 다시 시작하면 `published_at IS NULL` 행부터 가져가 발행 (`OutboxRelay`) | 릴레이 중간 종료 후 재시작 → 누락 없음, 중복은 재집계가 보정 | 밀린 양 확인 (지표) |
| 릴레이 여러 개 | 행을 잠그고 가져가기 (`SKIP LOCKED`) | 두 릴레이를 동시에 돌려도 같은 행을 한 번만 가져감 | 없음 |
| Kafka 다운 | 클릭 기록은 outbox 에 쌓이고 응답은 정상. 살아나면 릴레이가 밀린 것을 보냄 | Kafka 를 끈 상태에서 클릭 → outbox 에 쌓임 → 다시 켜면 발행됨 | 보관 기간 값 정하기 |

### 3-11. 롤업 (분 → 시간 → 일)

**무엇인가**: 분 단위 값을 시간 단위, 일 단위 표로 미리 합쳐 두는 것. 긴 기간(예: 한 달)을 조회할 때 분 단위 행을 수만 개 더하지 않게 한다.

**누가 하나**: **ClickHouse 구체화 뷰.** 집계는 ClickHouse가 하고, 스프링은 롤업을 만들지 않는다 (집계 규칙을 한 벌로 두는 원칙, 4-1). 스프링은 조회 API가 어느 표를 읽을지 고르기만 한다.

**언제 만드나 (보류, 조건부)**
- 지금: 불필요. 통계 API 는 최대 24시간 기간만 허용하므로 분 단위 표로 충분하다.
- 조건: 하루 넘는 기간 조회가 필요해지거나, 측정에서 분 단위 질의가 느리다고 확인될 때.

**만든다면 구조**
```
click_facts (분)  ──구체화 뷰──▶  click_facts_hour (시간)  ──구체화 뷰──▶  click_facts_day (일)
```
- 시간 표와 일 표도 `SummingMergeTree` 를 쓴다 (같은 키는 합산).
- 시간 표: `toStartOfHour(minute)` 로 묶고, 일 표: `toDate(minute)` 로 묶는다.

**주의: 재계산과 함께 맞춰야 한다**
- 재계산은 `click_facts` 의 날짜 파티션을 **교체**한다 (3-8). 구체화 뷰는 **원본 표에 새 행이 들어올 때만** 돈다. 그래서 교체만으로는 시간 표와 일 표가 옛 값으로 남는다.
- 해결: 재계산이 같은 날짜의 시간 표와 일 표도 교체한다 (분 표와 같은 방식으로 `REPLACE PARTITION`).
- 이 작업을 재집계 서비스의 cron 단계에 넣는다 (3-8 의 4번).

**결정 / 보류 / 미정**

## 4. 광고 선택 (멘토 피드백 "뭘 보여줄지")

**현재** (PR #111 이후): 연령대와 성별이 맞는 진행 중 캠페인 중 무작위 1개. 입찰가·예산 없음, 기본 배너 없음.

**확정된 결정 (2026-10-29)**
- 과금: **노출당 차감**. 노출 1회마다 입찰가만큼 캠페인 예산에서 뺌.
- 점수: **입찰가** 기준. 클릭률(CTR)은 점수에 넣지 않음 (노출당 과금이면 입찰가가 곧 수익).
- 선택: 입찰가에 비례한 **확률 뽑기**. 1등이 가장 자주 나오되 낮은 입찰가 광고도 가끔 나옴 (굶는 문제 완화).
- 시간대: **출근·퇴근만** 시간대 몫을 둠. 그 외 시간은 전체 예산 안에서 나감.
  - 출근: **06:00 ~ 09:00**, 퇴근: **17:00 ~ 20:00** (서버 한국 시간 기준)
  - **평일·주말 모두 적용**
- 빈 자리: **기본 배너**(예산·입찰 없음, 하우스 광고) 노출.
- 기간 종료 후 남은 예산: **환불 처리 대상으로 기록만** 함. 실제 환불은 결제 시스템 도입 때 구현 (이번 범위 밖).

**변경안**
```
1) 후보 조회: 기간 안 + 예산 남음 + 연령대·성별 일치 (+ 출퇴근 시간이면 시간대 몫 남음)
2) 확률 뽑기: 후보마다 입찰가에 비례한 확률로 1개 선택
3) 노출 기록: ad_impressions 저장
4) 예산 차감: 남은 예산이 입찰가 이상일 때만 조건부 차감 (한 번의 UPDATE)
     차감 실패 시 그 광고 탈락, 다음 후보로 재시도
5) 후보 0개 → 기본 배너 응답 (노출 기록 없음 또는 별도 표시)
6) 기간 종료 시 남은 예산을 환불 대상으로 기록
```

- 입찰가·예산 필드가 없으므로 `campaigns.bid_price`, `campaigns.budget` 등을 추가해야 합니다 (7절).
- 시간대 몫은 출근·퇴근 두 칸만 둡니다 (예: `campaign_time_shares(campaign_id, slot, share_pct)`).
- CTR은 나중에 "반응 좋은 광고 보정"으로 추가할 수 있습니다. 지금은 계산하지 않습니다.
- 굶는 문제: 확률 뽑기 가중치 계산식은 측정 후 조정. 사전값(노출 100, 클릭 1)은 CTR을 쓸 때만 필요하므로 지금은 불필요.

### 4-1. 용어

| 용어 | 뜻 |
|---|---|
| 노출 | 광고가 화면에 한 번 보인 것 |
| 입찰가 | 노출 1회마다 광고주가 내는 금액 (예: 1노출 = 10원) |
| 예산 | 캠페인 전체에 쓸 수 있는 총액 (예: 100만 원) |
| 시간대 몫 | 출근·퇴근 시간에 쓸 수 있는 **최대 금액** (상한). 확률이 아님 |
| 기본 배너 | 고를 광고가 없을 때 대신 보이는 우리 서비스 배너. 예산·입찰 없음 |
| 확률 뽑기 | 후보 중 입찰가에 비례한 확률로 1개를 고르는 방식 |

### 4-2. 광고 주는 쪽 입력 예시

| 항목 | 예시 |
|---|---|
| 총 예산 | 100만 원 |
| 입찰가 | 노출 1회당 10원 |
| 대상 연령대 | 20대, 30대 |
| 대상 성별 | 전체 (`all`) |
| 기간 | 11/1 ~ 11/30 |
| 출근 몫 | 50% → 50만 원까지만 출근 시간에 노출 |
| 퇴근 몫 | 30% → 30만 원까지만 퇴근 시간에 노출 |
| 그 외 | 나머지 20% → 20만 원 |

시간대 몫은 **총 예산 기준**입니다. 매일 리셋되지 않습니다. 출근 몫 50만 원은 기간 전체에서 한 번만 씁니다.

### 4-3. 사용자가 화면을 열 때 (한 번의 요청)

```
[사용자 요청: 나이대 20대, 여성, 지금 시각 7시 30분 (평일)]

1) 후보 모으기
   · 기간 안인가
   · 예산이 남았는가
   · 연령대가 맞는가 (20대)
   · 성별이 맞는가 (전체 or 여성)
   · 지금이 출근 시간(06~09시)이면: 출근 몫이 남았는가
   → 통과한 광고 = 후보

2) 후보가 0개 → 기본 배너 보여 주고 끝

3) 후보가 있으면 확률 뽑기
   · 후보마다 입찰가에 비례한 확률
   · 1개 선택

4) 차감 시도 (한 번의 조건부 UPDATE)
   · 남은 예산 ≥ 입찰가 이고, 출근이면 출근 몫 남음 → 차감 성공 → 노출 기록 → 광고 보여 줌
   · 실패 → 그 광고는 이번 요청에서 빠짐 → 남은 후보로 3)부터 다시

5) 남은 후보가 없으면 → 기본 배너
```

### 4-4. 숫자 예시

캠페인 3개가 있다고 합시다.

| 광고 | 대상 | 입찰가 |
|---|---|---|
| A | 20대·30대, 남녀 전체 | 100원 |
| B | 20대·30대, 남녀 전체 | 50원 |
| C | 50대, 남성 | 80원 |

| 사용자 | 후보 | 결과 |
|---|---|---|
| 25세 여성 (평일 오후 2시) | A, B | A 약 67%, B 약 33% |
| 55세 남성 | C | C 100% |
| 60세 여성 | 없음 | 기본 배너 |

- 확률 계산: A = 100 ÷ (100 + 50) = 약 67%, B = 50 ÷ 150 = 약 33%
- 같은 사용자가 다시 접속하면 확률을 **새로** 뽑습니다. A와 B를 번갈아 볼 수 있습니다.
- 한 번의 요청에는 광고가 **1개만** 나갑니다. 나머지는 그 요청에서만 빠집니다.

### 4-5. 나이대·성별이 겹칠 때

- 한 사람에게 맞는 광고가 여러 개면 그냥 경쟁합니다. 두 번째 광고가 같은 나이대여도 문제가 없습니다.
- "첫 번째 광고를 고른 뒤 나머지 사람에게 두 번째 광고를 준다"는 방식이 **아닙니다.** 사람마다 따로 후보를 모읍니다.
- 같은 사람에게 같은 광고가 반복되는 것은 빈도 제한으로 막을 수 있지만, 지금은 **보류**입니다.

### 4-6. 차감 방식

- 과금은 **노출당**입니다. 노출 1회 = 입찰가만큼 차감.
- 차감 조건은 한 문장으로 확인합니다.
  ```
  UPDATE campaign_budget
     SET spent_total = spent_total + :bid, am_spent = am_spent + :bid
   WHERE campaign_id = :id
     AND spent_total + :bid <= total_budget
     AND (출근이면) am_spent + :bid <= am_cap
  ```
  - 0행이 바뀌면 차감 실패 → 그 광고 탈락
- 요청이 많으면 같은 캠페인 행을 여러 요청이 기다립니다. 이 부분은 측정 후 판단합니다 (Redis 카운터 검토).

### 4-7. 기간이 끝나고 예산이 남으면

- 기간이 끝나면 남은 예산을 **환불 처리 대상으로 기록**합니다.
- 실제 돈을 돌려주는 기능은 결제 시스템을 붙일 때 만듭니다.
- 예산이 적게 나간 이유 (입찰이 낮음 / 타겟이 좁음 / 기본 배너가 많음 / 시스템 문제)를 구분하려면 노출 기록이 필요합니다. 노출 기록은 `ad_impressions` 에 남습니다.

### 4-8. 결정 완료 / 보류 / 미정

| 구분 | 항목 |
|---|---|
| 결정 완료 | 노출당 차감, 입찰가 기준 확률 뽑기, CTR 선택에 미사용, 출근 06~09시·퇴근 17~20시(평일·주말), 시간대 몫은 상한, 남은 몫 이월 없음, 기본 배너 1개, 환불은 기록만, 배너 칸 1개 |
| 보류 | 배너 3칸, 같은 광고 반복 막기(빈도 제한), 예산 페이싱 |
| 미정 | 기본 배너 내용과 담당자, 확률 가중치 계산식(측정 후), 차감을 DB로 할지 Redis로 할지(측정 후) |

**다음 단계로 미룸**: 빈도 제한(같은 사용자에게 같은 광고 반복 노출 금지), 예산 페이싱(하루 예산을 시간대에 고르게 쓰기). 책 범위 밖이므로 레퍼런스(arXiv 2503.06942 등)를 따로 본다.

## 6. ERD 변경안

> **정본:** ERD·데이터 형식의 최종 기준은 `ERD_데이터명세.md` 이다. 이 절은 설명용이며, 고칠 때는 정본을 먼저 고친다.

> 표기: **[지금]** = 분 버킷·필터·상위 N, **[입찰·예산]** = 4절 결정 반영, **[Kafka]** = Kafka 연결 단계, **[측정 후]**·**[P3]** = 나중.
> 각 항목의 **근거** 는 어떤 목차(`책_목차별_우리시스템_대응.md` 2절)에서 이 변경이 필요해졌는지 적은 것이다.
> 운영 DB 는 `ddl-auto: validate` 라서 아래 SQL 을 마이그레이션 파일로 따로 만든다 (6-5).

### 6-1. PostgreSQL

#### [지금] ① 기존 표에 열 추가: `ad_impressions`, `click_events`

```sql
ALTER TABLE ad_impressions
    ADD COLUMN age_group VARCHAR(16),
    ADD COLUMN gender    VARCHAR(8);

ALTER TABLE click_events
    ADD COLUMN age_group VARCHAR(16),
    ADD COLUMN gender    VARCHAR(8);
```

- 값: `age_group` 은 `10s`~`50s`, `gender` 는 `male`/`female`.
- 노출을 만들 때 `target_users` 의 값을 복사한다. `M`/`F` 로 저장된 옛 값은 `male`/`female` 로 바꾼다 (`BannerService.toGenderCode` 와 같은 규칙).
- 클릭은 연결된 노출의 값을 그대로 가져온다. 유저 정보가 나중에 바뀌어도 기록은 그대로 남는다.
- 기존 행은 NULL 로 두고, 6-5 백필로 채운다.
- **근거**: 2절 2-1 질의 (3), 2절 2-4 필터 요구. IP·국가는 수집하지 않으므로 넣지 않는다 (2절 2-4 결정).

#### [지금] ② 신규: `campaign_minute_stats` (분 버킷 표)

```sql
CREATE TABLE campaign_minute_stats (
    campaign_id    BIGINT       NOT NULL REFERENCES campaigns(campaign_id),
    minute_bucket  TIMESTAMP    NOT NULL,              -- 분 단위로 자른 시각 (초 = 0)
    age_group      VARCHAR(16)  NOT NULL,              -- 값이 없으면 'unknown'
    gender         VARCHAR(8)   NOT NULL,              -- 값이 없으면 'unknown'
    sent_count     BIGINT       NOT NULL DEFAULT 0,
    click_count    BIGINT       NOT NULL DEFAULT 0,
    updated_at     TIMESTAMP    NOT NULL,
    PRIMARY KEY (campaign_id, minute_bucket, age_group, gender)
);

CREATE INDEX idx_cms_minute ON campaign_minute_stats (minute_bucket);
```

- 행 1개 = 캠페인 · 분 · 연령대 · 성별 조합 1개. "전체" 행은 따로 두지 않고 행을 합해서 구한다.
- 그래서 클릭 1건은 행 1개만 올린다 (쓰기 1번). 노출·클릭 요청 안에서 같은 트랜잭션으로 UPSERT 한다 (기존 `campaign_stats` 와 같은 방식).
- `idx_cms_minute` 이유: 상위 N 은 **여러 캠페인에 걸쳐 시간 범위**로 읽는다. 키의 첫 칸이 캠페인이라 PK 만으로는 시간 범위 조회가 느리다.
- **근거**: 2절 2-1 질의 (1) "최근 M분 클릭 수", 2절 2-4 "상위 N". 2절 2-4에서 상위 N 을 지금 하기로 결정했다. 이 표 없이는 분 단위 질의 자체가 안 된다.

#### [지금] ③ 상위 N 질의 (새 표 없음)

```sql
SELECT campaign_id, SUM(click_count) AS clicks
FROM campaign_minute_stats
WHERE minute_bucket >= :from
  AND minute_bucket <  :to
  AND (:age    IS NULL OR age_group = :age)        -- 필터가 없으면 전체
  AND (:gender IS NULL OR gender    = :gender)
GROUP BY campaign_id
ORDER BY clicks DESC
LIMIT :n;
```

- 결과는 1분 동안 캐시한다 (요청마다 계산하지 않음). 캐시는 Redis 로 둔다 (그림대로).
- **근거**: 2절 2-4 (2) "매분 상위 N".

#### [지금] ④ 인덱스 정정 (기존 계획의 오류)

기존 `고도화_계획.md` 3-2 의 `ON campaigns (target_age_group, ...)` 는 **이제 없는 열**이다. 연령대·성별은 `campaigns` 가 아니라 `campaign_age_groups`, `campaign_genders` 표에 한 줄씩 있다. 그래서 인덱스도 그 표에 건다.

```sql
CREATE INDEX idx_campaign_age_groups_age ON campaign_age_groups (age_group, campaign_id);
CREATE INDEX idx_campaign_genders_gender ON campaign_genders (gender, campaign_id);
CREATE INDEX idx_click_events_campaign_time ON click_events (campaign_id, clicked_at);
CREATE INDEX idx_impressions_campaign_time  ON ad_impressions (campaign_id, shown_at);
```

- 배너 선택 질의 (`findRandomActiveForTarget`) 가 두 표를 `EXISTS` 로 읽으므로 연령대·성별 인덱스가 필요하다.
- 두 표의 기존 키 구성은 생성 전에 확인한다. 효과는 측정 때 `EXPLAIN (ANALYZE, BUFFERS)` 로 본다.
- **근거**: 2절 2-5 견고성·지연은 측정 항목. 3-2 DB 튜닝.

#### [지금] ⑤ 유지: `campaign_stats` (누적 한 행)

- 삭제하지 않는다. 대시보드의 누적 숫자 (SSE) 가 계속 읽는다.
- **근거**: 2절 2-1 "지금 코드" (누적 숫자만 있음). 분 버킷 합계와 맞는지 조정 쿼리로 비교한다 (2절 2-5).

#### [입찰·예산] ⑥ 입찰가·예산 (4절 결정 반영)

```sql
ALTER TABLE campaigns ADD COLUMN bid_price INT NOT NULL DEFAULT 0;   -- 노출 1회당 금액(원)

CREATE TABLE campaign_budget (
    campaign_id   BIGINT    PRIMARY KEY REFERENCES campaigns(campaign_id),
    total_budget  BIGINT    NOT NULL,              -- 총 예산(원)
    spent_total   BIGINT    NOT NULL DEFAULT 0,
    updated_at    TIMESTAMP NOT NULL,
    CHECK (spent_total <= total_budget)
);

CREATE TABLE campaign_slot_budget (
    campaign_id  BIGINT      NOT NULL REFERENCES campaigns(campaign_id),
    slot         VARCHAR(16) NOT NULL,              -- MORNING(06~09시) | EVENING(17~20시)
    slot_cap     BIGINT      NOT NULL,              -- 이 시간대에 쓸 수 있는 최대 금액 (총 예산 기준, 이월 없음)
    slot_spent   BIGINT      NOT NULL DEFAULT 0,
    PRIMARY KEY (campaign_id, slot),
    CHECK (slot_spent <= slot_cap)
);

CREATE TABLE refund_ledger (
    refund_id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    campaign_id  BIGINT    NOT NULL REFERENCES campaigns(campaign_id),
    remaining    BIGINT    NOT NULL,              -- 기간 종료 시 남은 예산 (기록만, 실제 환불은 결제 도입 후)
    recorded_at  TIMESTAMP NOT NULL
);
```

- 차감은 두 표를 한 트랜잭션에서 조건부 UPDATE 한다 (4절 4-6). 출퇴근 시간이 아니면 `campaign_slot_budget` 은 건드리지 않는다.
- 기존 4-6 SQL 의 `am_spent`, `am_cap` 열은 `campaign_slot_budget` 으로 옮겼다. 시간대가 두 개라 열보다 행으로 두는 것이 맞다.
- **근거**: 4절 결정 (노출당 차감, 시간대 몫은 상한, 남은 예산은 기록만). 2절 2-5 정확성 (차감 충돌 방지).

#### [입찰·예산] 기본 배너: 표 없음

- 내용과 담당이 미정이다 (4절 4-8). 설정 값으로 시작하고, 필요해지면 표로 만든다.

#### [Kafka] ⑦ outbox 표 (발행 누락 방지, 고도화 목표)

```sql
CREATE TABLE outbox_events (
    outbox_id       BIGSERIAL    PRIMARY KEY,
    event_type      VARCHAR(32)  NOT NULL,        -- 'CLICK' 등
    notification_id VARCHAR(36)  NOT NULL UNIQUE, -- 중복 발행 방지 키
    payload         JSONB        NOT NULL,        -- campaign_id, clicked_at, age_group, gender
    created_at      TIMESTAMP    NOT NULL,
    published_at    TIMESTAMP,                    -- NULL 이면 미처리
    attempts        INT          NOT NULL DEFAULT 0
);
CREATE INDEX idx_outbox_unpublished ON outbox_events (created_at) WHERE published_at IS NULL;
```

- **근거**: 2절 2-2 "시스템 일부 다운" (재처리 경로 없음), 2절 2-5 견고성. 클릭 저장과 Kafka 발행 사이의 누락을 막는 표다. 릴레이가 이 표를 읽어 Kafka 로 보낸다 (3-3 Kafka 연결).

#### ⑧ `top_ads_snapshot` — 만들지 않음 (6장: 메모리 상태가 없어 스냅숏 불필요) 【정정: DDL 은 참고용으로만 남김. 확정: 만들지 않음】

```sql
CREATE TABLE top_ads_snapshot (
    window_minutes  INT        NOT NULL,           -- 집계 구간 (1, 5 …)
    update_minute   TIMESTAMP  NOT NULL,           -- 갱신 시각 (분 단위)
    rank_no         INT        NOT NULL,           -- 1 = 가장 많이 클릭됨
    campaign_id     BIGINT     NOT NULL REFERENCES campaigns(campaign_id),
    click_count     BIGINT     NOT NULL,

```

- **윈도우**: `window_minutes` 는 1 이상의 정수이고 최대 60이다. 같은 `update_minute` 에 윈도우마다 한 줄씩 들어가며, 윈도우 1분·5분을 같은 표에 함께 저장한다 (3-6 윈도우 규칙).
- **근거**: 2절 2-4 (2) 상위 N, 책 6-2 스냅숏. 상위 N 조회가 측정에서 느리다고 나올 때 추가한다. 처음부터 넣지 않는다.

### 6-2. ClickHouse [Kafka 연결과 함께]

```sql
-- Kafka 에서 읽는 통로 (저장 안 함). 파티션 3 이므로 소비자도 최대 3
CREATE TABLE click_events_kafka (
    notification_id String,
    campaign_id     Int64,
    age_group       String,
    gender          String,
    clicked_at      DateTime
) ENGINE = Kafka
SETTINGS kafka_broker_list = 'kafka:9092',
         kafka_topic_list = 'click-events',
         kafka_group_name = 'clickhouse-group',
         kafka_format = 'JSONEachRow',
         kafka_num_consumers = 3;

-- 원본 (중복 제거). 같은 notification_id 는 한 줄로 합쳐짐
CREATE TABLE click_raw (
    notification_id String,
    campaign_id     Int64,
    age_group       LowCardinality(String),
    gender          LowCardinality(String),
    clicked_at      DateTime,
    ingested_at     DateTime DEFAULT now()   -- ClickHouse 가 받은 시각 (지연 측정용)
) ENGINE = ReplacingMergeTree
ORDER BY notification_id;

CREATE MATERIALIZED VIEW click_raw_mv TO click_raw AS
SELECT notification_id, campaign_id, age_group, gender, clicked_at
FROM click_events_kafka;

-- 대시보드가 읽는 집계 (분·연령대·성별 합계)
CREATE TABLE click_facts (
    campaign_id  Int64,
    minute       DateTime,
    age_group    LowCardinality(String),
    gender       LowCardinality(String),
    click_count  UInt64
) ENGINE = SummingMergeTree
PARTITION BY toYYYYMMDD(minute)
ORDER BY (campaign_id, minute, age_group, gender);

-- 재계산용 스테이징 (같은 구조)
CREATE TABLE click_facts_stage AS click_facts;

CREATE MATERIALIZED VIEW click_facts_mv TO click_facts AS
SELECT campaign_id, toStartOfMinute(clicked_at) AS minute, age_group, gender, count() AS click_count
FROM click_events_kafka
GROUP BY campaign_id, minute, age_group, gender;
```

- `click_facts_mv` 는 Kafka 메시지가 두 번 오면 두 번 더한다. 그래서 실시간 값은 **잠정**이고, 재집계 cron 이 같은 날짜를 `click_raw` 에서 다시 만들어 덮어쓴 값이 **확정**이다 (3-3 결정 4).
- 재집계는 날짜 단위로 `click_facts` 를 지우고 `click_raw` (중복 제거) 에서 다시 넣는다.
- **근거**: 책 3-2-4 (집계 DB), 4-2 (재계산), 5-5 (핫스팟 대비). 노출 표는 만들지 않는다 (노출은 PostgreSQL).

### 6-3. Redis 키 [그림대로, 조회 API 와 함께]

| 키 | 타입 | 내용 | TTL |
|---|---|---|---|
| `ad:clicks:{yyyyMMddHHmm}` | Sorted Set | campaign_id → 그 분의 클릭 수 | 2시간 |
| `ad:top:{window}:{yyyyMMddHHmm}` | Sorted Set | 윈도우 상위 결과 캐시 | 1분 |
| `campaign:candidates:{ageGroup}` | String(JSON) | 연령대별 후보 캠페인 목록 | 30~60초 |

- 상위 N 캐시와 후보 캐시는 Redis 로 한다 (그림대로). 앱 메모리 캐시는 쓰지 않는다.
- **근거**: 2절 2-4, 책 6-1 (결함 내성 시 상태 저장).

### 6-4. ID 체계 정리

| 항목 | 현재 | 제안 |

### 6-5. 운영 DB 적용 순서 [지금]

1. **열 추가** (NULL 허용). 기존 기능에 영향 없음.
2. **새 표 생성** (`campaign_minute_stats`, 인덱스).
3. **백필** (과거 데이터 채우기):
   - `ad_impressions`, `click_events` 의 `age_group`, `gender` 는 `target_users` 와 맞춰서 채운다.
   - `campaign_minute_stats` 의 과거 분 값은 `click_events.clicked_at`, `ad_impressions.shown_at` 으로 만들 수 있다.
   - 백필 SQL 은 로컬 PostgreSQL 16 에서 먼저 검증한다.
4. **구버전 서버 중지 → 새 버전 시작** (PR #111 때와 같은 순서).
5. **확인**: 백필 이후 기간에 `campaign_minute_stats` 합계가 `campaign_stats` 증가분과 같은지 확인 (2절 2-5 조정).
6. 운영 DB 작업은 사용자가 직접 한다 (운영 접근은 사용자만 있음).

## 10. 6장 적용 통합 정리 (책 목차 1~8절 → 우리 시스템)

> 이 절은 `책_목차별_우리시스템_대응.md` 의 내용을 옮긴 것이다. 각 항목은 **책 내용 → 지금 코드 → 적용 → 이유 → 결정** 순서다. 자세한 설계는 앞 절(3-x, 5, 6, 7) 번호를 따른다.
> 시스템 구조 그림: `시스템_아키텍처.png` (아래).

![시스템 아키텍처](시스템_아키텍처.png)

### 10-1. 1절 이 장이 다루는 것 (RTB, 집계 중요성)

- **책**: 광고 경매(RTB)와 클릭 집계. 집계는 광고 효율과 과금의 근거다.
- **지금**: 경매 없음. 배너는 연령대·성별이 맞는 캠페인 중 무작위 1개를 고른다 (`ORDER BY random()`).
- **적용**: 경매는 하지 않는다 (우리 범위 밖). 대신 **여러 광고 중 하나를 고르는 기준**만 가져온다 (4절 광고 선택, 입찰가 확률 뽑기).
- **이유**: 광고 노출이 한 번 나올 때마다 이기는 광고를 정하는 것이 목적이다. 실시간 경매 서버는 규모에 비해 과하다.
- **중요성**: 과금은 없지만 광고주가 숫자로 예산을 판단하므로 **정확성이 가장 중요**하다.

### 10-2. 2절 문제 이해와 설계 범위

**2-1 질문과 답**
- **책**: 입력은 여러 서버의 로그. 질의 3개 = (1) 광고 1개의 최근 M분 클릭 수, (2) 최근 1분 상위 100개, (3) 속성 필터.
- **지금**: 입력은 클릭 요청 1건씩 (로그 파일 아님). 질의는 누적 숫자 1쌍뿐 (`CampaignStatsStreamService`, SSE 2초).
- **적용**: (1) 분 버킷 표 `campaign_minute_stats`. (2) 상위 N 도 **지금** 한다 (분 버킷 합계 → 나중에 ClickHouse). (3) 필터는 **연령대·성별**만.
- **이유**: (1)(2)(3) 모두 광고주 대시보드 기능이다. 상위 N 을 나중으로 미루면 대시보드가 빈다.

**2-2 특이 상황**
- **늦은 이벤트**: 서버 수신 시각을 쓰므로 밀려서 늦게 오는 일이 없다 (처리 시각, 4-3).
- **중복**: `notification_id` UNIQUE + `ON CONFLICT DO NOTHING` (이미 있음). 새 클릭일 때만 집계.
- **장애**: 클릭 저장과 집계를 한 트랜잭션으로 묶어서 중간 실패는 롤백. 재처리는 6-3 복구에서 다룬다.
- **결정**: 중복 차단은 유지. 장애 복구는 3-10.

**2-3 지연 시간**
- **책**: 경매 1초 이내, 집계는 몇 분 이내.
- **지금**: 경매 없음. 대시보드 2초 갱신 (`stats.stream.interval-ms` 기본값 2000).
- **적용**: 2초 갱신 유지. 클릭 처리 지연은 **측정 전이라 값이 없다** (측정 후 채움, 3-1).
- **결정**: 대시보드 2초 유지. 처리 지연 지표는 모니터링(3-4)에 넣는다.

**2-4 기능 요구사항**

| 책의 요구 | 지금 | 적용 | 이유 |
|---|---|---|---|
| 최근 M분 광고별 클릭 수 | 없음 | 분 버킷 표 + 조회 때 합산 (4-5) | 저장을 1분 칸으로 하면 중복이 없음 |
| 최근 1분 상위 100 | 없음 | 분 버킷 합계로 지금 (`top-campaigns`) | 대시보드 기능 |
| 속성 필터 | 타겟 설정(연령대·성별 여러 개)은 있음, 집계 쪽은 없음 | 클릭·노출에 `age_group`, `gender` 열 추가 | 광고주가 타겟과 같은 기준으로 결과를 보게 함 |
| 데이터 양 (페이스북급) | 우리 규모 아님 | 가정으로만 사용 | 과설계 방지 |

- **IP·국가는 빼기로 결정**: 지금 수집하지 않고, 수집하려면 방식부터 새로 만들어야 한다. 개인 정보 부담도 크다. 광고주 기준(연령대·성별)과 맞춘다.

**2-5 비기능 요구사항**
- **정확성**: 같은 트랜잭션이라 기록과 집계가 어긋나지 않는다. 대신 **매일 맞춰 보는 조정**을 추가한다 (7-3).
- **중복·지연**: 중복은 막는다. 지연은 처리 시각 기준이라 문제없다.
- **견고성**: 지금은 DB 한 대. 장애 복구는 6절(3-10)에서 다룬다.
- **지연 시간**: 대시보드 2초로 충분.

**2-6 개략 계산**
- **책**: 하루 클릭 10억, 평균 1만 QPS, 최대 5만 QPS, 하루 100GB.
- **지금**: 실측 없음. `docs/ARCHITECTURE.md` 2-D 의 1,125건/초는 가정값 (유저 10만 명, 캠페인 200개, 클릭률 25%).
- **적용**: 책 숫자는 기준으로 쓰지 않는다. **부하 테스트 결과**로 한계를 잡는다 (3-1).
- **이유**: 우리 규모에서는 5만 QPS가 문제가 아니다. 같은 캠페인 행 잠금(핫 로우)이 훨씬 작은 부하에서 먼저 드러날 수 있다 (5-5).
- **목표 규모**: 측정값의 2배 (임시, 8절 1번).

### 10-3. 3절 개략 설계안

**3-1 질의 API**
- **책**: `GET /v1/ads/{ad_id}/aggregated_count`, `GET /v1/ads/popular_ads`.
- **지금**: 둘 다 없음. 통계는 SSE 하나.
- **적용**: `GET /api/v1/campaigns/{campaignId}/stats/timeseries` (A1), `GET /api/v1/stats/top-campaigns` (A2). 인증은 `@AdvertiserId` (내 캠페인만). `ad_id` 대신 `campaignId`.
- **이유**: 대시보드 기능에 필요. 책의 `filter` 번호 대신 연령대·성별 인자.

**3-2 데이터 모델**
- **3-2-1 원시**: `click_events` 있음. `age_group`, `gender` 열 추가 (6-1 ①). IP·국가 없음 (2-4).
- **3-2-2 집계**: 누적 한 행뿐 → `campaign_minute_stats` 신규 (6-1 ②). 책의 `filter_id` 표는 필요 없다. 연령대·성별 열이 곧 필터이기 때문이다.
- **3-2-3 원시와 집계 둘 다**: 유지. 재계산(4-2)을 하려면 원시가 필요하다. 원시는 S3 에도 보관한다.
- **3-2-4 DB 선택**: 책은 카산드라나 InfluxDB를 말한다. 우리는 **PostgreSQL (지금) → ClickHouse (집계) + S3 (원본)**로 역할을 나눈다. 카산드라는 쓰지 않는다. 이유: ClickHouse 와 S3 가 같은 역할을 맡는다. 두 DB를 더 두면 운영만 늘어난다.

**3-3 개략 설계 (큐, 비동기)**
- **책**: 큐 1 → 집계 서비스 → 큐 2 → DB 기록. 큐 2는 집계 결과를 원자적으로 넣기 위해서다.
- **지금**: 큐 없음 (동기).
- **적용 (확정)**:
  - **큐 1 = Kafka `click-events`** (파티션 3, 키 `campaign_id`). 클릭 처리 서비스가 outbox 를 거쳐 보낸다 (outbox 는 저장과 발행 사이 누락을 막기 위해 둔다).
  - **집계는 ClickHouse 구체화 뷰**가 한다. 앱에서 분 단위로 묶지 않는다.
  - **큐 2 없음**. 이유: 앱 집계가 없으므로 다시 보낼 중간 결과가 없다.
  - **합치기 방식 없음**. 이유: ClickHouse 가 `SummingMergeTree` 로 합산하고, 상위 N 도 SQL 로 정렬한다.
  - **앱 소비자는 재집계 서비스 1개** (Kafka 읽기 + S3 저장 + cron).
  - **노출은 Kafka 로 보내지 않음**. 그림도 클릭만 있다. 노출 수는 PostgreSQL 에 동기 UPSERT.
- **원자성**: 큐 2 없이도 ClickHouse 구체화 뷰와 재집계 보정으로 최종 값을 맞춘다.

**3-4 집계 서비스 안쪽 (MapReduce)**
- **책**: 여러 서버가 나눠 세고 합친다.
- **지금**: 앱 한 대. 나눠 셀 대상이 없다.
- **적용**: 구현하지 않는다. 합치기 방식도 쓰지 않는다 (3-3).

### 10-4. 4절 상세 설계 (4-1 ~ 4-7)

요약 표는 **3-9절**에 있다. 여기서는 이유만 적는다.

- **4-1 람다**: 실시간(ClickHouse) + 일괄(재집계). 이유: 그림이 그렇게 되어 있고, 재계산 경로가 필요하다. 집계 규칙을 SQL 한 벌로 맞춘다 (로직 두 벌의 단점을 줄임). 카파는 재계산도 스트림으로 해야 하므로 우리 방식이 아니다.
- **4-2 재계산**: 재집계 서비스의 cron 이 S3 원본을 ClickHouse 가 읽게 해서 날짜 파티션을 `REPLACE PARTITION` 으로 교체 (3-8). 이유: 교체는 한 번에 바뀌어 대시보드가 빈 값을 보지 않는다. 같은 날짜를 여러 번 돌려도 같다 (멱등). 구체화 뷰 롤업(3-11)도 함께 교체해야 한다.
- **4-3 시간**: **처리 시각** (서버가 요청을 받은 시각)을 `clicked_at` 으로 쓴다. 이유: 클라이언트 시각은 조작될 수 있고, API·프론트를 다시 바꿔야 한다. 우리는 온라인 클릭이라 차이는 네트워크 지연(수 초)뿐이다. 오프라인 클릭 기능이 생기면 다시 본다.
- **4-4 워터마크**: 실시간에는 두지 않는다. 늦은 클릭은 도착한 분 칸에 더해지고, 재집계가 최근 48시간을 다시 계산해서 확정한다. 48시간 넘는 누락은 조정(7-3)에서 드러난다. 이유: 구체화 뷰는 칸을 닫는 개념이 없다.
- **4-5 윈도우**: 저장은 1분 텀블링 칸, 최근 M분은 조회할 때 합산. 윈도우는 1분 배수, 최대 60분. 저장하지 않는 이유: 행이 M배로 늘고, 겹치는 값을 더하면 중복이 생긴다 (3-6).
- **4-6 전달 보장**: 실시간은 **최소 한 번** (잠정 값). 확정 값은 재집계로 **결과적으로 정확히 한 번**. 실시간 정확히 한 번(Kafka 트랜잭션)은 **보류**. 이유: 구현과 비용이 크다. 확정 값으로만 과금한다 (과금을 붙일 때).
- **4-7 중복 제거**: ① 클라이언트 중복은 `notification_id` 로 막는다 (이미 적용). ② 시스템 중복은 실시간에서 허용하고 `click_raw` 와 재집계의 `GROUP BY notification_id` 로 정리한다. 책의 오프셋 저장 방식(해결 1~3)은 **쓰지 않는다**. 이유: 분산 트랜잭션은 과하고, 재집계가 같은 결과를 더 단순하게 만든다. ③ 광고 사기 탐지는 **나중 과제**.
- **4-8**: 책에는 없다. 예산 차감 동시성은 우리 항목이며 아직 확정하지 않았다 (정할 것 참고).

### 10-5. 5절 규모 확장

- **5-1 성장 가정 (연 30%)**: 우리는 성장 가정을 세우지 않는다. 측정 결과로 "지금 한계의 몇 배까지 되는지"만 본다. 이유: 발표·데모 규모라 가정이 근거가 없다.
- **5-2 메시지 큐 확장**: 파티션 **3개로 시작**, 몰리면 **늘릴 수 있다**. 키는 `campaign_id`. 늘릴 때는 소비자가 잠깐 멈춰서 다시 나눠 맡는다. 합산은 ClickHouse 가 하므로 결과는 깨지지 않는다. 릴레이를 여러 개 돌리면 `SKIP LOCKED` 로 같은 행을 한 번만 가져간다.
  - 이유: 처음에 "파티션을 바꾸면 안 된다"고 한 것은 합치기 방식 때문이었다. 합치기가 없어졌으므로 제약이 사라졌다.
- **5-3 집계 서비스 확장**: 집계는 ClickHouse 가 한다. 재집계 서비스는 여러 개로 늘려도 된다 (S3 저장만 하므로 중복은 재집계가 보정). YARN 같은 자원 관리자는 필요 없다.
- **5-4 DB 확장**: 지금은 PostgreSQL 한 대와 ClickHouse. 쓰기 한계가 측정되면 (1) 분 버킷 파티셔닝, (2) 집계를 ClickHouse 로 옮기기 순서로 본다. 카산드라는 쓰지 않는다 (3-2-4).
- **5-5 핫스팟**: 두 곳.
  - ① 요청 경로: 같은 캠페인의 `campaign_stats` 행 잠금. 1단계는 분 버킷으로 나누고, Kafka 연결로 요청 경로에서 뺀다 (근본 해결).
  - ② Kafka 파티션: 큰 캠페인이 한 파티션에 몰린다. 측정에서 밀리면 키에 해시를 붙여 나눈다 (예: `12-0`, `12-1`, `12-2`). ClickHouse 가 합산하므로 결과는 같다.
  - 측정 항목: 잠금 대기 수, 파티션별 밀린 메시지 수, 캠페인별 클릭 비율.

### 10-6. 6절 결함 내성

- **6-1 집계 상태**: 우리 집계는 앱 메모리에 상태를 두지 않는다. 상태는 ClickHouse와 PostgreSQL에 있다. 이유: 죽어도 DB 값은 남는다. 앱에는 캐시(Redis)만 있고 캐시는 다시 채우면 된다.
- **6-2 스냅숏**: **만들지 않는다** (`top_ads_snapshot` 제거). 이유: 메모리 상태가 없어서 복구할 스냅숏이 필요 없다. 상위 N 은 ClickHouse 에서 다시 계산한다. 나중에 소비자가 메모리에 분 값을 들고 계산하는 방식으로 바꾸면 그때 다시 본다.
- **6-3 복구 절차**: 책은 "새 노드, 스냅숏 복구, 큐에서 다시 읽기"다. 우리는 구성 요소마다 "멈출 때 무엇이 멈추고, 살아날 때 어떻게 따라잡나"를 코드로 만든다 (3-10 표).
  - 핵심: 릴레이는 미발행 행부터, 재집계는 48시간 재계산, ClickHouse 다운은 PostgreSQL 경로로 자동 전환, Redis 다운은 원본 조회, Kafka 보관 기간은 S3 장애를 견딜 만큼 길게.

### 10-7. 7절 데이터 모니터링과 정확성

- **7-1 왜 중요한가**: 광고주가 보는 숫자이므로 틀린 숫자를 조용히 보여 주지 않는 것이 목표다.
- **7-2 지표**: 우리 지표 이름, 측정 위치, 방법은 **3-4절**에 있다. 핵심은 처리 지연(`ingested_at − clicked_at`), outbox 대기 시간, Kafka lag, 재계산 성공과 최근 성공 시각, 조정 차이.
  - 도구: Actuator + Micrometer → Prometheus → Grafana (Prometheus·Grafana 는 P3). ClickHouse 쪽 값은 앱이 조회해서 노출한다.
- **7-3 조정**: 매일 세 값을 비교한다. PostgreSQL `click_events` 수, S3 고유 `notification_id` 수, ClickHouse `click_raw` 수. **허용 오차 0.** 차이가 나면 경고. 두 단계로 나눠 보면 어디서 빠졌는지 찾을 수 있다.
- **7-4 최종 설계도**: 그림(`시스템_아키텍처.png`)에 **조정**과 **지표 수집**이 빠져 있다. 그림을 고칠 때 넣는다 (PR).

### 10-8. 8절 대안 설계 (Hive, ClickHouse, Druid, Flink)

- 책의 대안: 원시는 Hive, 집계는 ClickHouse 또는 Druid, 중간에 Flink.
- 우리: 원시는 **S3** (Hive 대신), 집계는 **ClickHouse** (구체화 뷰). **Flink 없음**. 위험 통제 엔진 없음 (광고 사기 탐지는 나중 과제).
- 이유: Flink 가 하던 실시간 집계는 ClickHouse 가 맡는다. 스프링 워커는 집계를 하지 않는다 (집계 로직 두 벌 방지). 복잡한 창 처리나 실시간 사기 탐지가 필요해지면 Kafka Streams 나 Flink 를 다시 본다.

### 10-9 롤업

- 지금은 만들지 않는다 (통계 API 최대 24시간). 필요해지면 ClickHouse 구체화 뷰로 분 → 시간 → 일을 만든다. 재계산 때 같이 교체한다 (3-11).
