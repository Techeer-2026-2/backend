### 0-1. 측정 전에 맞출 데이터 양

측정 결과는 데이터 양에 따라 달라지므로, 단계마다 **같은 양**으로 맞춘다.

| 항목 | 기준선과 같은 값으로 유지 | 확인 쿼리 |
|---|---|---|
| `target_users` 행 수 | ___ 명 | `SELECT count(*) FROM target_users;` |
| `campaigns` 행 수 (진행 중) | ___ 개 | `SELECT count(*) FROM campaigns WHERE status='ACTIVE' AND deleted_at IS NULL;` |
| 측정 대상 캠페인 ID (클릭이 몰리는 캠페인) | ___ | |

| `click_events` 행 수 (측정 시작 시점) | ___ | `SELECT count(*) FROM click_events;` |

> 추천 초안: 타겟 유저 1,000명, 진행 중 캠페인 100개 (연령대·성별을 섞어서), 클릭 대상 캠페인 1개. 실제 값은 기준선 실행 전에 정해서 여기에 적는다.
> 측정 **전에** 데이터를 초기화하거나, 측정 후 쌓인 행 수를 기록한다. 이전 실행 데이터가 섞이면 결과가 틀어진다.

## 2. 측정 방법 상세

### 2-0. 준비

- 도구 설치: `brew install k6` (부하), `psql` (DB 쿼리).
- DB 통계 확장 확인: `pg_stat_statements` 가 켜져 있어야 "가장 많이 실행된 SQL" 을 볼 수 있다. 꺼져 있으면 `CREATE EXTENSION pg_stat_statements;` 와 `shared_preload_libraries` 설정이 필요하다 (Docker 설정 변경, 기준선 전에 확인).
- 앱 지표: Actuator 는 지금 `health,info` 만 열려 있다 (develop 기준). **HikariCP 대기 수와 지연 히스토그램을 보려면** 측정 기간 동안 `metrics` (또는 `prometheus`) 노출이 필요하다. 이 설정은 측정용 프로필에서만 열고, 운영 설정에는 넣지 않는다.
- 테스트용 토큰: 시나리오 C 와 캠페인 생성에는 광고주 토큰이 필요하다. `POST /api/v1/owners/login` 으로 받아서 스크립트 환경변수에 넣는다.

### 2-1. 시나리오 A: 노출 (`GET /api/v1/banners/match`)

- 요청: `GET /api/v1/banners/match?targetUserId={id}` (인증 없음)
- 대상 유저 ID 는 `target_users` 에서 무작위로 고른다 (같은 유저만 반복하면 같은 행을 계속 갱신해서 결과가 왜곡된다).
- 기대 응답: `200` (배너), `204` (매칭 없음). **204 도 정상 응답으로 센다.** 에러율에는 넣지 않는다. 대신 "배너 있음 비율"을 따로 기록한다.
- 측정 항목:
  - 응답 시간 p50 / p95 / p99 (k6 `http_req_duration`)
  - 에러율 (5xx, 타임아웃)
  - 배너 있음 비율 (200 / 전체)
- 이 시나리오가 건드리는 쿼리: 유저 조회, 캠페인 무작위 선택 (`ORDER BY random()`), 노출 INSERT, `campaign_stats` UPSERT (같은 캠페인 행을 모든 요청이 잠금).

### 2-2. 시나리오 B: 클릭 (`POST /api/v1/clicks`)

- **주의: 클릭은 노출에서 받은 `notificationId` 가 있어야 한다.** 그래서 B 는 "노출 요청 → 받은 notificationId 로 클릭" 순서로 한 쌍을 만든다.
- 요청: `POST /api/v1/clicks`, 본문 `{"notificationId": "..."}`
- 응답 코드:
  - `201` = 새 클릭 (이 시나리오에서 재야 하는 것)
  - `200` = 같은 notificationId 의 중복 클릭 (별도로 기록하는 값)
  - `404` = 노출 기록 없음 (에러로 센다)
- **중요:** 같은 notificationId 를 여러 번 보내면 대부분 중복(200)이 되어 **다른 경로**를 잰다. 반드시 노출 한 번당 클릭 한 번으로 만든다.
- 측정 항목:
  - 새 클릭(201) 의 응답 시간 p95
  - 중복 클릭(200) 의 응답 시간 p95 (참고용)
  - 에러율 (5xx, 404)
  - **잠금 대기 수** (아래 2-5)
- 이 시나리오가 건드리는 것: `click_events` INSERT (`ON CONFLICT`), `campaign_stats.click_count` UPSERT (같은 캠페인 행 잠금), 같은 트랜잭션.

### 2-3. 시나리오 C: 대시보드 SSE (`GET /api/v1/campaigns/{id}/stats/stream`)

- 요청: `GET /api/v1/campaigns/{id}/stats/stream`, 헤더 `Authorization: Bearer {광고주 access token}`
- 응답: `text/event-stream`, 이벤트 이름 `stats`, 2초마다 한 번 (기본값 `stats.stream.interval-ms=2000`).
- **k6 는 SSE 를 길게 유지하는 데 제한이 있으므로**, C 는 다음 중 하나로 한다 (스크립트 방식은 0단계에서 정함):
  - (a) `curl -N` 을 구독자 수만큼 띄우고, 각 연결이 몇 개의 `stats` 이벤트를 받는지 센다.
  - (b) 작은 Java/Node 클라이언트로 구독자 N명을 열고 이벤트 수와 지연을 기록한다.
- 측정 항목:
  - 구독자 수 (N)
  - DB 조회 수/초 (아래 2-5 의 `pg_stat_statements` 에서 `campaign_stats` 조회 호출 수)
  - 이벤트 도착 지연 (서버가 보낸 시각과 클라이언트가 받은 시각 차이, 가능하면)
  - 서버 CPU (`docker stats` 또는 Activity Monitor)
- 확인할 값: 구독자가 N명일 때 `campaign_stats` 조회가 **N/2초 배**로 늘어나는지. 고도화(M1) 후에는 캠페인당 1회로 줄어야 한다.

### 2-4. 시나리오 D: 혼합

- A, B, C 를 동시에 돌린다. 각 시나리오의 값은 1절과 같다.
- 목적: 단독 측정에서는 안 보이던 **서로 간섭**(같은 캠페인 행 잠금 + SSE 조회)을 확인.

### 2-5. DB 쪽 관찰 (모든 시나리오 실행 중에 같이)

| 확인 대상 | 쿼리 / 방법 | 기록할 값 |
|---|---|---|
| 잠금 대기 수 | `SELECT count(*) FROM pg_stat_activity WHERE wait_event_type = 'Lock';` (측정 중 여러 번 샘플링) | 최댓값, 평균 |
| 가장 많이 실행된 SQL | `SELECT query, calls, mean_exec_time, total_exec_time FROM pg_stat_statements ORDER BY calls DESC LIMIT 10;` | 상위 10개 (측정 후 한 번) |
| 잠금이 걸린 행 | `pg_locks` 와 `pg_stat_activity` 를 조인 | 어느 테이블·행인지 (스크린샷) |
| 실행 계획 (단계 1 이후) | `EXPLAIN (ANALYZE, BUFFERS) <쿼리>` | 실행 시간, 읽은 버퍼 수 |

> 측정 전에 `pg_stat_statements_reset()` 으로 통계를 비우고 시작하면, 실행이 끝났을 때 그 시나리오만의 통계가 남는다.

### 2-6. 앱 쪽 관찰 (지표 노출을 켰을 때)

| 지표 | 의미 | 기록할 값 |
|---|---|---|
| `hikaricp_connections_pending` | DB 연결을 기다리는 요청 수 | 최댓값 (0 이어야 정상) |
| `hikaricp_connections_active` | 사용 중인 연결 수 | 최댓값 |
| `http_server_requests_seconds` | 엔드포인트별 응답 시간 | p95 (k6 값과 비교) |
| `process_cpu_usage` | 프로세스 CPU | 최댓값 |

## 6. 체크 규칙

- 단계 측정은 **이전 단계 코드가 머지된 뒤**에 한다.
