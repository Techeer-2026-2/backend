## 왜
요구사항은 "시간대·날씨 + 위치(주변 랭킹)" 추천이다. #92 에서는 랭킹 곡 ID 와 iTunes 곡 ID 의 연결이 정해지지 않아 뺐고, 연결 합의를 기다리면 기능이 계속 밀려서 먼저 구현했다.

## 결정
- 후보 자격은 분위기 적합도로만 정한다. 가산점은 후보 안에서 뽑힐 확률만 올린다. 분위기에 맞지 않는 인기곡은 들어오지 못한다
- 가산점 = 0.5 × 차트 범위 강도 × (곡 청취자 수 ÷ 차트 1위 청취자 수). 적합도에 `× (1 + 가산점)` 을 곱한다
- 범위 강도: 내 셀 1.0 / 상위 셀 0.7 / 도시 0.5 / 전체 0.25. 집계 전·데이터 부족·빈 차트는 0 (숫자는 초안)
- 랭킹 곡 ID 는 `itunes-123` 과 `123` 을 모두 같은 곡으로 본다. 팀 합의 전이라 한쪽으로 고정하지 않았다
- 기준 위치는 요청의 위도·경도(둘 다 있어야 함)를 우선하고, 없으면 통근 프로필 출발지다. 위치는 저장하지 않는다
- 랭킹 조회가 실패해도 추천은 가산점 없이 계속한다. 응답 `context.popularity` 에 반영 여부·범위·반영된 곡 수를 담는다. 가산점을 받는 후보가 이번 후보 안에 없으면 `applied=false`

## 대안
| 대안 | 기각 이유 |
|---|---|
| 별도 "주변 인기곡으로 만들기" 엔드포인트 | 홈의 TOP 50 은 프론트가 랭킹 API 를 직접 부르면 되고, 추천과 따로 두면 분위기 필터가 빠진다 |
| 랭킹 곡을 후보에 직접 추가 | 우리 곡 카탈로그·분위기 점수가 없는 곡이 들어온다 |

## 한계
랭킹 데이터가 데모뿐이고 노출 기준(지역 청취자 20명·곡 3명)이 높아 대부분 전체 차트로 fallback 되어 효과가 작다. 랭킹 곡이 우리 `tracks` 에 없으면 효과가 없다.

## 되돌릴 조건
랭킹 곡 ID 형식이 팀에서 정해지면 한 형식만 받게 정리하고, 가산점 크기는 실제 데이터가 쌓인 뒤 다시 정한다.
