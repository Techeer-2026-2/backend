# 작업 기록 (`docs/context/`)

AI 와 대화하며 정한 **구현 방식과 이유**를 남기는 곳입니다. 나중에 기능을 고도화하거나 추가할 때 "어떻게 만들었고 왜 그렇게 했는지"를 대화를 다시 하지 않고 읽어서 알기 위한 것입니다.

## 읽는 법 (토큰을 아끼기 위해 단계별로만 읽는다)
1. `docs/context/INDEX.md` — 구역 목록
2. 해당 구역의 `INDEX.md` — 기록 한 줄 요약 표
3. 관련 기록 1~2개만 연다

## 구역

| 구역 | 넣는 것 | 하위 폴더 이름 |
|---|---|---|
| `dev/` | 구현 방식, 알고리즘, 버그 원인과 해결, 실험 결과 | 코드 패키지 이름 (`domain/<이름>`)과 같게 |
| `design/` | DB·API 설계, 트레이드오프, 기각한 대안 | `db`, `api` 등 |
| `etc/` | 운영·외부 서비스·팀 합의·일정 | 자유 |

## 무엇을 기록하나

| 기록한다 | 기록하지 않는다 |
|---|---|
| 구현 방식과 **이유**, 기각한 대안 | 잡담, 오타 수정, 시행착오 과정 |
| 실험 결과와 숫자 | API 키·비밀번호·토큰·개인정보 |
| 버그의 원인과 해결 | 코드를 읽으면 바로 아는 내용 |
| 한계와 되돌릴 조건 | 사람에 대한 평가 |

세 가지를 모두 만족할 때 기록합니다: ① 되돌리기 어렵다 ② 코드만 봐서는 이유를 모른다 ③ 진짜 대안이 있었다.
(새 의존성·외부 서비스·DB 방식·인증 방식을 고르면 무조건 기록합니다.)

## 규칙 (`scripts/check-docs.sh` 가 PR 에서 자동으로 검사한다)

- 파일 이름: `YYYY-MM-DD-영문-slug.md` (`id` 와 같아야 함). 번호 대신 날짜를 쓰는 이유는 PR 여러 개가 동시에 기록을 추가해도 이름이 겹치지 않게 하기 위해서입니다.
- 위치: `dev/`, `design/`, `etc/` 아래. 파일의 `zone` 값이 폴더와 같아야 합니다.
- 본문(맨 위 `---` 블록과 빈 줄 제외)은 **30줄 이하**. 길어지면 줄이지 말고 **결정을 둘로 나눕니다.**
- 맨 위 `---` 블록에 필수 항목: `id`, `title`, `zone`, `status`, `recorder`, `recorded`, `discussed`, `refs`, `summary`
- 만든 기록은 **그 구역의 `INDEX.md` 표에 한 줄 추가**해야 합니다. 구역 `INDEX.md` 가 40줄을 넘으면 하위 폴더 INDEX 로 나눕니다.
- 키·비밀번호 같은 문자열이 들어 있으면 검사가 실패합니다.
- **상태**: `제안` → (팀 리뷰 후) `확정` / `폐기` / `대체됨`. 확정된 기록은 고치지 않고 **새 기록을 만들어 `대체됨`으로 바꿉니다.**
- 기록과 코드가 다르면 **코드가 사실**입니다. 기록을 대체하세요.

## 누가 쓰나
결정이 나면 AI 가 초안을 만들고 사람(`recorder`)이 확인합니다. PR 을 올릴 때 그 PR 의 결정 기록을 같은 PR 에 포함하고, PR 설명에 기록 `id` 를 적습니다. 원하면 언제든 "이거 기록해"라고 요청해도 됩니다.

양식은 [`TEMPLATE.md`](TEMPLATE.md) 를 복사해서 씁니다.
